검색 엔진과 저장 구조

“전송 계층에서 빠진 데이터는 어떻게 처리했지?”라는 질문을 따라가 보세요. 캐시미가 어떤 기록을 먼저 읽고 어느 문장을 답변의 근거로 쓰는지 살펴봅니다.

원문과 색인세 가지 검색 단서RRF 계산기근거 검토실행과 권한백업과 복구

저장 버튼을 누르면 무엇이 남을까?

기록의 본문과 수정 이력은 SQLite에 남습니다. 검색용 데이터는 저장이 끝난 뒤 원문에서 다시 만들어집니다.

  1. SQLite에 기록“TCP는 누락된 데이터를 재전송한다”는 본문, 기록 ID, 현재 버전, 색인 작업을 함께 저장합니다.
  2. Markdown 분할짧은 글은 한 구간으로 둡니다. 긴 글은 제목·절, 블록, 문장 경계를 따라 나누고 각 구간의 원문 시작·끝 위치를 기억합니다.
  3. LanceDB에 색인청크마다 제목·절과 본문을 합친 검색용 텍스트, 벡터, 원문 버전·위치·색인 세대를 씁니다. 준비된 기록이 검색 후보가 됩니다.

본문을 고치면

수정본이 새로운 현재 버전이 됩니다. 검색은 SQLite의 버전·세대가 일치하는 준비 완료 구간만 채택합니다. 새 색인을 만드는 중에는 예전 구간이 최신 답변의 근거로 나오지 않습니다.

색인 도중 앱이 꺼지면

SQLite에 남은 작업을 다시 읽습니다. 실행 중인 작업의 임대 시간이 지나면 다시 가져올 수 있습니다. 이미 더 새 버전이 생긴 작업은 건너뜁니다. 실패한 최신 작업은 다시 시도할 수 있습니다.

원문 위치와 토큰 예산 펼치기

한 청크의 모델 입력은 제목·헤더·특수 토큰을 포함해 최대 512토큰입니다. 제목과 헤더 맥락은 최대 64토큰이며 큰 블록을 강제로 나눌 때만 최대 64토큰을 겹칩니다. 원문 위치는 유니코드 문자 기준 [시작, 끝)입니다. 검색용으로 덧붙인 제목은 인용할 본문 범위에서 빠집니다.

어떤 단서로 후보를 찾을까?

‘전송 계층’이라는 말, ‘빠진 데이터’의 뜻, 공부할 때 연결한 주제가 각각 다른 기록을 찾아냅니다. 서버는 하나의 질문 임베딩을 만들고 본문 검색과 주제 탐색을 병렬로 진행합니다.

낱말이 겹치는 구간

ICU 전문 검색 · BM25

LanceDB가 텍스트를 낱말로 나눠 질문과 겹치는 청크를 찾습니다. 예를 들어 “재전송”이라는 낱말이 어느 구간에 나오는지가 단서입니다. 상위 40개 구간을 가져옵니다.

뜻이 가까운 구간

KURE-v2 · MaxSim

CPU에서 질문과 청크를 토큰별 128차원 벡터로 만듭니다. 질문 토큰마다 가장 가까운 청크 토큰과의 코사인 유사도를 찾아 합칩니다. ‘빠진 데이터’와 ‘누락된 패킷’처럼 다른 표현도 후보가 됩니다. 상위 40개 구간을 가져옵니다.

이름이 맞는 주제

SQLite 연결 · 본문 구간 확인

질문 속 ‘전송 계층’이 저장된 주제 이름이나 별칭과 맞으면 그 주제에 연결된 기록도 탐색합니다. 주제는 최대 3개, 주제마다 최근 갱신된 유효 기록 최대 5개를 살피고 기록별로 질문에 가장 가까운 청크를 찾습니다.

필터, 한국어 처리, 현재 검색의 범위

유형·주제·사건 날짜 조건은 세 경로에 공통으로 적용합니다. 주제 이름과 별칭의 앞뒤 경계, 한국어 조사를 확인하며 여러 주제가 공유하는 모호한 별칭은 건너뜁니다. 특정 본문 구간에만 붙은 주제라면 해당 범위와 겹치는 부분에서 근거를 고릅니다.

본문 키워드 경로는 LanceDB의 ICU 토크나이저를 쓰며 어간 변환·불용어 제거·ASCII 접기는 끕니다. 의미 경로는 벡터 인덱스를 우회해 필터를 통과한 후보에서 정확 검색합니다. 짧은 식별자나 한국어 표현 차이 때문에 두 경로가 모두 놓치는 기록도 있습니다.

서로 다른 검색 순위를 어떻게 합칠까?

낱말 검색의 BM25 점수와 의미 검색의 코사인 유사도는 척도가 다릅니다. 캐시미는 각 목록에서 몇 번째로 등장했는지를 사용합니다. 이 방식이 Reciprocal Rank Fusion(RRF)입니다.

각 경로의 기여 = 1 ÷ (60 + 순위)
1위는 1/61, 2위는 1/62입니다. 한 경로에 없으면 기여는 0입니다. 같은 후보의 기여를 모두 더한 뒤 큰 값부터 읽습니다.

  1. 구간 순위 합치기낱말 목록과 의미 목록에서 같은 청크 ID의 기여를 더합니다. 같은 기록의 여러 청크는 기록 한 건으로 묶고, 가장 먼저 나온 구간 점수와 일치한 모든 범위를 보관합니다.
  2. 기록 순위 합치기주제 후보가 있으면 본문 기록 순위와 주제 기록 순위를 같은 공식으로 다시 합칩니다. 이때 입력은 두 목록의 순위입니다. 주제 후보가 없으면 첫 단계에서 얻은 기록 순위를 그대로 반환합니다.

직접 계산해 보기

세 기록에서 구간 하나씩을 찾았다고 가정합니다. A는 ‘TCP 재전송’, B는 ‘UDP 손실 실험’, C는 ‘전송 계층 비교’입니다. 예시 순위를 바꿔 같은 기록이 두 경로에 나타날 때 결과가 어떻게 달라지는지 확인하세요.

최종 순위와 단계별 RRF 점수
최종 순위기록본문 단계최종 점수
1위B0.0163930.032266
2위A0.0325220.016393
3위C0.0320020.016129

본문 1위 A의 점수는 의미 2위와 낱말 1위에서 온 1/62 + 1/61 = 0.032522입니다. 최종 1위 B의 점수는 본문 3위와 주제 1위에서 온 1/63 + 1/61 = 0.032266입니다.

본문에서 놓친 기록도 나타날까?

의미 순위를 ‘A → B’, 낱말 순위를 ‘후보 없음’, 주제 순위를 ‘C → A’로 골라 보세요. C는 본문 단계 점수가 비어 있어도 주제 1위의 기여로 최종 목록에 들어옵니다. 실제 검색에서도 의미·낱말의 상위 40개 목록에서 모두 빠진 기록을 연결된 주제에서 다시 발견할 수 있습니다.

점수와 동점을 읽는 법

0.032266은 이 질문에서 기록을 읽을 순서를 정하는 값입니다. 답변의 정확도나 확률로 환산할 수 없습니다. 합산값이 같으면 본문 결합에서는 청크 ID, 최종 결합에서는 기록 ID를 오름차순으로 정렬합니다. 예시는 양쪽 모두 A, B, C 순서의 ID를 사용합니다. 표는 소수점 여섯 자리까지 표시하고 순위는 반올림하기 전 값으로 정합니다.

이 계산기는 순위 목록을 입력받아 실제 결합식을 재현합니다. 예시 기록의 순위는 설명용으로 설정했습니다. 제품은 RRF 다음에 별도의 교차 인코더나 언어 모델로 후보 순위를 다시 매기지 않습니다. 답변을 작성할 때는 별도로 근거를 검토합니다.

검색 결과가 어떻게 인용이 될까?

“UDP가 손실을 복구했다”는 기록을 찾았다고 해봅시다. 당시 응용 프로그램이 복구한 것인지, 전송 프로토콜이 보장한 것인지는 문장 주변과 실험 조건을 읽어야 알 수 있습니다.

  1. 원문에서 읽기서버가 SQLite에서 현재 버전과 본문 범위를 확인합니다. 근거에 기록 ID, 버전 ID, 시작·끝 위치를 붙이고 관련 구간이나 적용 조건을 함께 읽습니다.
  2. 근거에 번호 붙이기LangGraph 에이전트가 읽기 전용 검색과 다시 읽기 도구를 사용합니다. 요청 안에서 발급된 근거 번호로만 저장 지식에 관한 주장을 인용할 수 있습니다.
  3. 문단별 검토모델이 질문·근거·답변 문단을 대조합니다. 뒷받침되지 않는 문단을 제외하고 조사하지 못한 범위를 표시합니다. 서버는 반환 직전에도 버전과 관계 상태를 다시 확인합니다.

질문하는 동안 원문이 바뀌면

답변을 준비하는 동안 근거의 버전·상태·색인 세대가 바뀌면 서버가 현재 답변을 무효화합니다. 새 검색은 수정된 기록으로 시작합니다.

이미 발행한 아티클에서는

인용은 작성 당시 읽은 저장본과 구간을 계속 가리킵니다. 출처 패널에서 당시 문장을 읽고 현재 기록을 따로 확인할 수 있습니다. 삭제된 원문의 본문은 출처에서 열 수 없습니다.

질문 길이와 근거 수의 한계

직접 검색하는 질의는 모델 입력 64토큰까지입니다. 웹 질문은 긴 원문을 보존하고 짧은 검색 단위로 나누며 아직 확인하지 못한 부분을 추적합니다. 한 요청의 읽기 도구는 최대 8회입니다. 근거 수집에는 최대 10개 기록, 20개 구간, 본문 20,000자 한도가 있습니다. 답변은 사용자가 저장을 선택할 때 기록이 됩니다.

내 기기와 모델은 어디에서 연결될까?

동작별 실행 위치와 필요한 연결
동작실행 위치와 입력
저장·목록·열람로컬 FastAPI가 SQLite를 읽고 씁니다. 웹 서재와 Codex MCP가 같은 기록 서비스에 접근합니다.
색인·검색설정의 ‘검색 기능 준비’에서 고정한 KURE-v2 파일을 내려받거나 준비된 로컬 파일을 읽습니다. 이후 문서·질의 임베딩과 LanceDB 검색은 CPU에서 실행됩니다.
질문·근거 검토웹에서 연결한 ChatGPT 계정의 선택 모델에 질문과 도구로 읽은 근거·관계 등 필요한 맥락을 전달합니다. 연결과 검색 준비 상태가 필요합니다.
자동 주제 분류외부 모델에 분류할 기록의 본문과 후보 주제 정보를 전달합니다. 연결이 없거나 분류가 실패해도 원본 저장은 유지됩니다.
접근 권한과 계정

기본 서버는 127.0.0.1:52761에서 대기합니다. 웹 요청의 Host·Origin을 확인하며 웹 세션과 변경 요청용 CSRF 토큰을 사용합니다. Codex의 MCP 요청은 별도 로컬 Bearer 토큰으로 인증합니다. ChatGPT 연결은 OAuth PKCE를 사용하고 계정·모델을 한 곳에서 관리합니다.

사용자 데이터 디렉터리는 운영체제별 경로를 따릅니다. POSIX에서 새 데이터 디렉터리는 소유자 전용 모드 0700, 인증 JSON은 0600으로 생성합니다. 이 권한은 운영체제의 파일 접근 제어입니다. 운영체제·CPU별 설치 가능 여부는 PyTorch, LanceDB 등 네이티브 의존성에도 영향을 받습니다.

다른 컴퓨터에서는 어떻게 이어갈까?

백업 ZIP에 들어가는 것

cache-me.sqlite3 스냅샷에는 기록·버전·주제·관계·아티클과 내부 삭제 이력이 있습니다. manifest.json에는 스키마·임베딩 프로필 정보와 DB 파일의 SHA-256이 들어갑니다.

새 기기에서 준비할 것

로그인 비밀, 모델 가중치, LanceDB 검색 색인은 백업에서 제외됩니다. 새 기기에서 모델을 준비하고 색인을 다시 만들며, 외부 모델을 쓸 때 다시 로그인합니다.

  1. 백업 다운로드실행 중인 서재의 설정에서 ‘내 데이터 → 백업 다운로드’를 선택합니다. SQLite의 일관된 스냅샷이 만들어집니다.
  2. 빈 경로에 배치같은 버전을 새 기기에 준비하고, 첫 서버 실행 전에 빈 데이터 디렉터리에 백업의 SQLite 파일을 같은 이름으로 놓습니다.
  3. 서재 확인서버를 시작해 원문을 연 뒤 설정에서 검색 기능을 준비합니다. 원문이 다시 검색되는지 확인합니다.

현재 복구 절차는 새 환경에 전체 스냅샷을 배치하는 방식입니다. 기존 서재와 합치는 가져오기 화면이나 삭제 기록을 개별 복원하는 휴지통은 제공하지 않습니다.

이 설명과 대응하는 구현

chunking.py·embedding.py가 청크와 벡터를 만듭니다. search.py의 _body_candidates, _topic_candidates, search가 두 차례 순위 결합을 정의합니다. topic_retrieval.py는 주제 후보의 상한과 이름 규칙, questions.py는 문단별 검토와 재검증, main.py는 접속 검사와 백업 파일 구성을 담고 있습니다.
