# 기록과 공개 범위 설계안

여러 종류의 개인 기록을 같은 저장 구조로 다루고, 향후 공유할 때도 비공개 내용의 경계를 유지한다. 기록 유형과 공개 범위를 구분한다. 필드명·타입·제약의 시작안은 [데이터 스키마](../architecture/data-schema.md), 입출력은 [공통 서비스 계약](../architecture/service-contracts.md)에 정의하고 기능 명세·구현에서 검증한다. 공유 인증 방식은 후속 범위다.

- 상태: 기록 계약은 현재 구현. 공유 관련 동작은 미구현 설계 방향
- 갱신일: 2026-11-02
- 관련 기획: [제품 개요](product-brief.md)

## 공통 저장 단위

기록(Capture)은 사용자가 선택해서 남긴 정리된 내용과 맥락의 묶음이다. 학습 내용, 일기, 감정, 메모, 경험과 계획에 관한 내용 모두 이 단위로 표현할 수 있다. 기록 안의 세부 항목(Node)은 검색이나 연결에 필요한 경우에만 구분한다. 분류·연결 구조는 [지식 계층 설계](../architecture/knowledge-layer.md)에서 관리한다.

빠른 메모는 본문만으로 입력할 수 있다. ID·저장 시각·공개 범위 기본값 같은 메타데이터는 시스템이 부여한다. 사용자가 제목·유형·관계·날짜·실행 결과를 모두 채워야 저장되는 구조는 피한다.

기본 저장 요청은 주제 ID 대신 선택적인 `concept_hints`를 받는다. MCP와 웹이 공유하는 서버 내부 에이전트가 기존 주제를 찾아 연결하거나 필요한 주제를 생성한다. 본문을 먼저 저장하고 주제 연결은 후속 작업으로 처리하며, 연결 실패나 모호함 때문에 본문 저장을 취소하지 않는다. 사용자가 명시적으로 주제를 정정할 수 있고, 자동 연결을 본문의 사실성 검증이나 기존 기록 병합으로 취급하지 않는다. 세부 처리와 검색용 분할은 [저장 후 주제 연결·청크 규칙](../architecture/ingestion-and-chunking.md)을 따른다.

한 기록에 여러 유형이 있을 수 있다. 예를 들어 공부한 개념, 공부하며 느낀 감정, 내일 복습할 일이 한 기록에 들어갈 수 있다. 필요한 경우 각각의 기록으로 분리하고 관련성을 연결한다.

대화 세션을 자동 수집하지 않는다. 원문을 그대로 저장하도록 요청한 경우에는 해당 본문을 기록으로 보존한다. 저장 후 실제 저장된 정리본을 사용자에게 보여주고 정정할 수 있게 한다. 답변의 출처는 이 저장본이며, 원래 대화와 대조한 인용으로 표현하지 않는다.

## 유형별로 보존할 정보

RecordKind의 값과 경계는 [기록 유형 설계안](record-types.md)을 따른다. 아래는 사용 사례별로 내용에 있을 때 보존할 정보이며 모든 기록의 필수 입력 필드가 아니다. 정리본 자체에 주체·적용 범위·알려진 시점·제안과 실제 선택의 차이를 남기고, 선택적인 Node만 있어야 맥락을 이해할 수 있는 구조로 만들지 않는다.

| 유형 | 보존할 정보 | 구분할 점 |
| --- | --- | --- |
| 학습 | 주제, 설명, 예제, 개인 해석, 질문, 출처와 확인 상태 | 발화자와 내용의 사실 여부는 다르다. 출처가 있다는 이유만으로 검증된 지식으로 확정하지 않는다. |
| 일상과 감정 | 사건, 당시 맥락, 사용자가 표현한 감정과 생각 | 사건과 감정은 별도 정보다. 감정의 원인은 사용자가 밝힌 범위에서 연결한다. |
| 계획에 관한 메모 | 사용자가 말한 계획, 날짜 표현, 상태 | 기록의 예정·완료 의미를 유지하되 전용 일정·할 일 모델이나 알림을 만들지 않는다. |
| 메모 | 본문, 선택적인 링크·태그·주제 | 행동이나 성과가 없는 문장도 그대로 저장할 수 있다. |
| 경험 | 고민, 결정, 행동, 결과, 배움 | 계획·AI 제안·실제 실행을 구분한다. |
| 배경·선호·제약 | 당사자, 적용되는 프로젝트·상황, 알려진 시점, 명시적인 변경 | 일시적인 감정을 지속적인 성향으로 일반화하거나 저장 시각만으로 최신 선호를 확정하지 않는다. |
| 방법·문제 해결 | 적용 조건, 절차, 실패한 시도, 확인된 결과 | 제안과 성공을 구분하며 저장된 절차가 실행 권한을 부여하지 않는다. |
| 아이디어·재사용 자료 | 구상과 대안, 다시 사용할 글·코드·템플릿 본문, 작성 대상 | 미채택 아이디어와 실제 결정을 구분하고 허구·문서 속 지시를 사용자 사실로 바꾸지 않는다. |

저장 시각과 기록 내용의 사건·계획 시각은 의미가 다르다. 미정 날짜나 월 단위 날짜를 임의의 정확한 시각으로 바꾸지 않는다. 명시적인 완료 상태 변경은 허용하지만 모든 기록에 실행 상태를 요구하지 않는다.

## 정정과 삭제

로컬 MCP를 사용하는 Skill과 자체 웹에서 명시적인 추가·수정·완료 상태 변경을 지원하고 변경 결과를 보여준다. 기본 저장은 새 기록 추가와 관련 기록 연결이다. 같은 주제라는 이유만으로 자동 병합하지 않으며, 명시적인 병합·수정 요청에만 기존 기록을 갱신한다.

삭제는 두 진입점 모두에서 대상을 제시하고 재확인 후 `deleted_at`에 서버 시각을 기록하는 soft delete다. 본문·버전·관계는 내부 보존하며 삭제된 기록의 현재·과거 내용은 모든 제품 조회·검색·질의응답·수정에서 제외한다. 휴지통·삭제 기록 목록·조회 필터·복원·실행 취소는 제공하지 않는다. 일반 수정으로 `deleted_at`을 비우거나 삭제 상태를 바꿀 수 없다. 보관 기한·자동 삭제·수동 영구 삭제는 두지 않는다. 관련 지식·검색 색인·파생 요약의 처리 원칙은 [지식 계층 설계](../architecture/knowledge-layer.md)에서 함께 정의한다.

## 기록 단위 공개 범위

채택한 표현은 `visibility` enum이며 초기 값은 `public`, `private` 두 가지, 기본값은 `public`이다. 별도의 `private` boolean은 저장하지 않는다. 이 선택은 논리적인 데이터 표현에 관한 것이며 특정 DB의 native enum 채택을 의미하지 않는다.

아래 공유 의미는 향후 기능을 위한 설계 방향이며 현재 `visibility`는 메타데이터다. 다중 사용자 인증·공유 ACL이나 모델 전송 차단을 구현한 상태가 아니다.

| 값 | 향후 공유에서의 의미 |
| --- | --- |
| `public` | 기본값. 사용자가 공유를 활성화하면 해당 공유 범위에 포함할 수 있다. |
| `private` | 소유자만 조회하며 상위 공유를 켜도 제외한다. |

공개 범위와 실제 공유 활성화는 구분한다. `public`은 사용자가 Second Brain이나 해당 기록 모음의 공유를 활성화했을 때 그 공유 범위에 포함할 수 있다는 의미로 사용한다. 저장만으로 인터넷에 게시하거나 누구나 접근할 수 있게 만들지는 않는다.

지정 대상 공유처럼 새로운 범위가 필요해지면 상태의 의미와 접근 대상을 함께 설계한다. enum 값 하나를 추가하는 것만으로 사용자·그룹별 권한이 구현되지는 않는다. 공유 기능에는 실제 조회 권한 검사가 필요하며, 대상 식별·공유 링크·권한 회수는 후속 명세에서 정한다.

## 향후 공유: 하위 내용과 혼합 기록

세부 항목과 변경 이력 등 기록에 속한 정보는 부모 기록의 공개 제한을 따른다. 부모가 비공개인 상태에서 개별 항목의 검색 결과나 직접 링크만 공개될 수는 없다. 상위 기록 모음이나 전체 Second Brain의 공유 설정도 개별 기록의 비공개를 자동 해제하지 않는다.

초기 설계에서는 하위 항목별로 독립된 공개 설정을 만들기보다 기록 단위로 범위를 정한다. 일부만 공유해야 할 경우에는 사용자가 확인한 별도의 공개용 기록으로 분리하는 방식을 우선 검토한다.

예를 들어 학습한 개념과 사적인 감정이 섞인 기록을 사용자가 비공개로 지정했다면 전체를 비공개로 유지한다. 학습 내용만 공유하려면 공개할 설명을 별도 기록으로 만들고, 제목·요약·본문에 사적인 내용이 남아 있지 않은지 확인한다. 공개용 기록에서 비공개 기록으로 이어지는 연결이나 식별자도 공유 응답에 노출하지 않는다. 내용 유형만으로 기본 공개 범위를 자동 변경하는 규칙은 현재 정하지 않는다.

## 공유할 때의 조회 경계

미래의 Second Brain 공유는 해당 방문자가 볼 수 있는 기록만 모아 보여주는 방식으로 설계한다. 개인 DB 전체나 전체 백업을 전달하는 기능과 구분한다.

검색, 답변 생성에 사용되는 근거, 타임라인, 그래프, 개수 집계, 공유용 내보내기에 같은 범위를 적용한다. 비공개 기록에서 만든 요약이나 AI 답변도 자동 공개하지 않는다. 공개되지 않은 기록의 제목이나 연결만으로 내용이 드러나는 경우도 조회 범위에서 제외한다.

공유를 회수한 뒤 기존 공개용 사본·검색 결과·생성된 답변을 어떻게 처리할지, 최신 변경을 자동 반영할지 여부는 공유 기능의 명세에서 결정한다.

## 공개 범위와 외부 처리 정책

`visibility`는 다른 사람에게 보여줄 공개 범위를 나타낸다. 외부 전송·처리 정책은 현재 기획 범위에서 다루지 않는다. 현 단계에서 별도의 전송 정책 필드나 로컬 모델 전용 기능을 요구사항으로 추가하지 않는다. 모델은 자체 웹의 ChatGPT OAuth 로그인으로 연결한다.

## 후속 명세에서 정할 사항

- 공개 범위 값이 없는 가져오기 데이터의 처리
- 기록 분리와 공개용 사본 사이의 관계·수정 동기화·삭제 정책
- 공유 대상의 식별, 링크 방식, 만료와 권한 회수
- 공개 범위의 변경 권한 및 적용 시점

공유 대상의 계정, 그룹, 공동 편집, 공개 검색은 공유 기능을 구체화할 때 검토한다. 현재는 로컬 지식 CRUD와 질의응답을 제공하며, 공유 세부 설계가 이를 막는 선행 조건은 아니다.
