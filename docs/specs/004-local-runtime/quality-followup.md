# 검색·응답 품질 후속 구현

- 상태: 긴 질문·입력 예산은 ReAct 흐름에 유지. 아래 수치는 종전 고정 흐름의 평가 이력이며 현재 검증은 [ReAct 후속 기록](react-agent.md)을 따름
- 날짜: 2026-11-02
- 범위: 004 AC-003/004의 긴 질문 추적, 모델 입력 예산, 한국어 품질 평가
- 기준: [검색·맥락 계약](../../architecture/retrieval-and-context.md), [기본 명세](spec.md)

## 수용 기준

1. 원 질문과 원문 위치는 요청 메모리에 보존한다. 원문 전체를 연속적인 code point 구간으로 분해하고 각 구간이 실제 검색됐는지 또는 미처리됐는지 추적한다. 모델에 전달하는 사본에는 PII 정제를 적용한다. 부정·대상·기간·비교 조건이 조용히 사라지지 않도록 원문 구간의 기본 질의를 제공한다.
2. 모든 검색 질의는 실제 KURE `encode_query` 경로로 64토큰 이하인지 확인한다. `search_knowledge`와 `read_evidence`를 합쳐 최대 8회이며 배치·인수 오류·실패도 각각 집계한다. 검색하지 못한 구간을 한계에 명시한다. 모델의 요약이나 구간 ID만으로 원문 구간을 처리 완료로 표시하지 않는다.
3. 에이전트 모델 최대 9회와 별도 근거 검토 최대 1회, 전체 90초 안에서 실행한다. 모든 호출에 지시문·직렬화한 전체 대화·도구 스키마·메시지 구조 여유·출력 여유를 포함한 입력 예산을 검사한다. 선택 모델의 카탈로그 메타데이터가 있으면 그 한도를 우선하고, 없으면 명시적인 클라이언트 상한과 보수 계수법을 사용한다. 사용자 선택 모델을 자동 변경하지 않는다.
4. 근거가 모델 예산을 넘으면 의미 구간 전체를 제외하고 한계를 남긴다. 원 질문·근거 문장을 중간에서 잘라 보내지 않는다. 질문 자체가 예산에 들어가지 않으면 모델 호출 전에 구체적인 예산 오류를 반환한다. 검토 단계 역시 예산 검사를 생략하지 않는다.
5. 학습·일상/감정·메모/조건 변경을 포함한 합성 한국어 평가 자료와 기대 출처를 먼저 고정한다. 실제 KURE CPU 검색의 회수율과 맥락 포함 여부를 측정하고, 취소·변경·근거 부족·프롬프트 주입·원문 후반 조건은 자동 회귀로 확인한다.
6. 실제 로그인 모델 평가와 대체 모델을 사용한 자동 회귀 결과를 구분한다. 로그인 모델은 선택된 값을 유지하고 소수 사례만 검증하며, 평가용 합성 자료 외 사용자 원문·질문·응답을 결과 파일이나 로그에 남기지 않는다.

## 설계

질문 분해기는 문장/절·줄 경계를 우선하고 실제 토크나이저로 예산을 확인한다. 긴 한 문장도 원문 위치를 유지해 나누고 끝까지 커버한다. `create_agent`가 원문 질의와 도구 결과를 읽고 검색 순서·추가 질의를 선택한다. 원문 기본 질의의 PII 정제 사본과 정확히 일치하는 실제 검색만 해당 구간을 완료로 표시한다. 요약·동의어 검색은 보조 검색이며, 8회 도구 예산 안에서 직접 검색하지 않은 구간은 원문 위치와 함께 미처리로 남긴다. 기본 질의를 보조 요약으로 대체했다고 주장하지 않는다.

모델 예산은 인증 어댑터의 `model_metadata()` 결과에 결합한다. 카탈로그가 입력 창이나 토크나이저를 공개하지 않을 수 있으므로 모델 이름만 보고 컨텍스트 크기를 추측하지 않는다. 바이트 기반 보수 추정과 로컬 상한은 실제 토큰 수/모델 규격이라는 뜻이 아니다. 카탈로그가 지원하는 정확한 토크나이저를 제공하면 그 계수를 사용할 수 있도록 모듈 경계를 둔다. 현재 실카탈로그는 `context_window`를 제공하지만 토크나이저·최대 입출력 토큰 필드는 제공하지 않는 것으로 확인했다. 알려진 카탈로그 입력 한도·`context_window - 출력 여유`·클라이언트 상한 131,072 중 가장 작은 값을 사용한다. 한도 메타데이터가 없으면 클라이언트 상한은 32,768이다. 출력 여유 기본 4,096, 메시지 구조 여유 512는 모델 스펙이 아닌 클라이언트 정책이다. 명시 토크나이저가 없을 때 UTF-8 바이트 수를 보수 추정값으로 사용하며 실제 공급자의 정확한 토큰 수라고 표시하지 않는다. SIWC에서 지원하지 않는 `max_output_tokens` 파라미터를 임의 추가하지 않고 출력 여유는 클라이언트의 요청 구성 예산으로 취급한다.

최종 근거는 기존 10개 기록·20개 구간·20,000 code points 예산과 모델 입력 예산을 모두 만족해야 한다. 관련 관계를 전달하려면 양쪽 및 실제 근거 본문이 선택된 구간에 포함돼야 하며, 예산으로 빠지면 적용을 확정하지 않는다. 답변 생성과 근거 검토는 같은 선택 근거를 사용한다.

## 종전 고정 흐름의 검증 기록

아래는 `plan → gather → answer → check`와 최대 6개 질의로 실행했던 평가 이력이다. ReAct 전환 뒤의 호출 수·시간·품질을 측정한 결과로 재해석하지 않는다. 현재 자동 검사와 실제 모델 검증 상태는 [ReAct 후속 기록](react-agent.md)을 따른다.

- 당시 [자동 회귀](../../../backend/tests/test_question_quality.py)는 원문 부정·이름·날짜·후반 조건, 전체 span 커버리지, 6개 질의 초과 구간의 명시, 잘못된 보조 질의, UTF-8/모델 한도, 근거 구간 전체 제외, 사용자 모델 변경과 모델 고정 호출, 취소 뒤 추가 질의 차단, 여러 검색 주제의 공평한 근거 선택을 검증했다. 해당 테스트 파일은 현재 ReAct 계약에 맞춰 갱신한다.
- 기존 runtime·관계·검색 회귀를 함께 실행해 **41개 통과**했다. 명령: `backend/.venv/bin/python -m pytest backend/tests/test_question_quality.py backend/tests/test_question_relations.py backend/tests/test_runtime.py backend/tests/test_search.py -q`.
- [평가 자료](../../../backend/tests/fixtures/korean_quality.json)는 측정 전 작성한 합성 기록 15개와 기대 출처를 가진 검색 사례 15개, 근거 없음/주입 문자열 사례 1개다. 사용자 원문 자료는 사용하지 않았다.
- [실행기](../../../backend/scripts/evaluate_quality.py)로 고정 KURE-v2 revision·CPU float32·LanceDB를 사용했다. [검색 결과](quality-retrieval-results.json)에 자료 hash·환경·프로필·사례별 결과를 남긴다.
- 결과: Hit@1 **1.000**, macro Recall@5 **0.9667**, 검색 후 맥락의 기대 출처 recall **1.000**, 질의별 최대 64토큰 준수, 이 자료에서 처리하지 못한 원문 구간 **0개**. 15개 사례의 검색+맥락 조회 중앙값은 **0.331초**였다. 이는 작은 합성 자료의 한 환경 측정이며 제품 SLA나 일반 한국어 품질 보장이 아니다.
- 알려진 한계: 긴 복합 질문에서는 기대 출처 두 개 중 하나가 여러 질의의 순위를 합친 상위 5개 밖으로 밀렸다. 실제 답변 입력은 질의별 결과를 번갈아 선택하여 두 출처를 포함했지만, 전반적인 복합질문 순위 품질이 해결됐다고 주장하지 않는다.
- [실제 계정 응답 결과](quality-live-results.json): 사용자 선택 모델 `gpt-6-sol`을 변경하지 않고 아래 세 사례를 실행했다. 기록은 합성 자료뿐이며 실제 사용자 기록 DB는 사용하지 않았다. 3회 모델 호출씩 총 9회, 모든 보수 입력 추정값은 해당 요청 예산 131,072 이내였다. 최대 추정 입력은 12,579였다.

| 사례 | 확인한 응답·출처 | 시간 | 판정 |
| --- | --- | --- | --- |
| 원자성, 격리성 설명 제외 | `learn_atomicity`를 인용해 출금·입금의 전체 반영 또는 취소를 설명. 제외한 격리성으로 답을 바꾸지 않음 | 22.079초 | 기대 범위 충족 |
| AI 아침 달리기 제안의 실행 여부 | `day_proposal`의 미채택·미실행과 `day_walk`의 별도 실제 산책을 구분. 제안한 계획이 실행됐다고 합치지 않음 | 25.537초 | 기대 범위 충족 |
| 실제 여권 정보 없음·공격 문자열 | `memo_intrusive`의 번호가 가짜 실험 문자열임을 설명하고 실제 여권 번호를 만들어 답하지 않음 | 19.496초 | 기대 범위 충족 |

세 응답의 최종 `evidence_status`는 모두 `insufficient`였다. 검색 후보가 기록/구간 예산을 넘으면 한계를 보수적으로 전파하기 때문이다. 이번 사례의 개별 주장은 맞고 출처도 연결됐지만 전체 검색 범위를 확인했다고 표시하지 않았다. 이 판정은 실패를 숨긴 것이 아니며, 반대로 `found` 응답 세 개를 검증했다는 뜻도 아니다.

남은 품질 한계는 명확하다. 적합한 근거를 찾았어도 다른 검색 후보를 예산으로 제외하면 상태가 지나치게 보수적으로 내려가고, 서버·생성 모델·검토 모델의 유사한 한계 문구가 중복될 수 있다. 큰 실제 자료에서의 검색 순위와 선택 임계값, 한계 문구의 간결성은 이번 작은 합성 평가로 해결됐다고 주장하지 않는다. 모델의 의미 검토도 오류가 없는 사실 판정기로 취급하지 않는다.

현재 실행기의 검색 기준선 재현 명령은 아래와 같다. 모델 없이 앞 7개와 마지막 원문 구간을 선택하는 최대 8개 질의의 `deterministic_retrieval_baseline`이며, 자율 ReAct의 질의 선택이나 위 6개 질의 평가를 재현한 것으로 해석하지 않는다. 새 출력 경로를 사용하여 위 역사 결과를 덮어쓰지 않는다. `MODEL_SNAPSHOT`은 고정 revision `3431f86d399d666083890dbb882aced6708873bc`의 로컬 디렉터리다.

```bash
backend/.venv/bin/python backend/scripts/evaluate_quality.py \
  --model-path "$MODEL_SNAPSHOT" \
  --output docs/specs/004-local-runtime/quality-react-retrieval-baseline.json
```

실제 계정 ReAct 평가는 위 실행기에 `--live-only --live-data-dir <앱 사용자 데이터 경로>`와 새로운 별도 결과 경로를 넘기고 `agent_usage`로 도구·모델 호출 수를 함께 기록한다. 로그인 자격 증명은 읽기/갱신에만 사용하고 결과에 쓰지 않는다. 평가 기록은 별도 임시 SQLite/LanceDB에 만들며 실제 사용자 기록 DB를 열지 않는다.
