# 기록 저장·조회·정정·소프트 삭제 명세

- 기준: [제품 기획](../project/product-brief.md), [도메인 용어](../project/domain-language.md), [공통 서비스 계약](../architecture/service-contracts.md), [데이터 스키마](../architecture/data-schema.md)

## 문제와 목표

Codex와 대화하며 정리한 내용 또는 자체 웹에서 작성한 내용을 같은 로컬 저장소에 남긴다. 저장 결과를 그대로 확인하고 이후 정정할 수 있어야 하며, 에이전트가 저장할 때 제공한 주제·Node·출처를 다시 읽을 수 있어야 한다.

목표는 두 진입점이 동일한 생성·조회·정정·출처 재검토·삭제 규칙을 사용하는 것이다. 원본 AI 대화 세션은 별도로 수집하지 않으며 사용자에게는 실제 커밋한 정리본을 보여준다.

## 범위

포함:

- 본문만으로 기록 생성, 선택적인 유형·주제 힌트·Node·출처 저장, 현재 기록 목록·상세 조회.
- 서버 내부의 저장 후 주제 탐색·연결 작업, 명시적인 주제 연결 정정. 외부 저장 요청자의 주제 ID 탐색을 필수로 하지 않음.
- 삭제되지 않은 기록의 과거 revision 조회, 명시적인 수정·완료 상태 변경·병합.
- 주제 생성·검색·조회·이름과 별칭 정정 및 기록·Node 연결, 근거가 있는 관계 생성·조회·명시적 철회.
- 구조화된 상세 응답과 출처 상태 반환, SourceRef가 지정한 저장본·구간 조회, 명시적인 출처 재검토로 새 정리본·출처 집합 생성.
- 사용자 재확인 후 `deleted_at`을 설정하는 soft delete, 재시도 중복 방지·수정 충돌 감지.
- 위 동작을 공통 도메인 서비스, MCP 도구, 웹 API에서 일관되게 제공.
- 기록 변경과 검색 반영용 작업을 같은 SQLite 트랜잭션에 저장하고 현재 검색 준비 상태 반환.

제외:

- 휴지통, 삭제 기록 목록·조회 필터, 복원·실행 취소, 자동 삭제·영구 삭제.
- 전체 대화 세션 보관, 자동 의미 병합, 자동 장기 기억 추출, 일정·알림 관리.
- 검색·답변·로그인과 화면의 세부 구현은 [런타임](runtime.md)과 [화면](workspace.md) 명세에서 관리한다.
- 사용자 공유·다중 사용자 권한 제품, 파일 첨부·실행, 자동 백업·프로필 병합.

웹과 MCP는 아래 기록 도메인 계약을 공유한다. 검색·답변·화면의 수용 기준은 별도 명세를 따른다.

사용자에게 저장 단위는 **기록**, 그 불변 내용은 **기록 버전**, 본문의 선택적 의미 구간은 **세부 항목**, 분류와 별칭은 **주제**로 설명한다. 코드의 `Capture`, `CaptureRevision`, `Node`, `Concept`와 대응하며 기존 API·MCP·저장 식별자는 유지한다. `state_version`은 수정 충돌을 검사하는 **상태 버전**으로 기록 버전과 구분한다.

## 요구사항

### 입력과 저장 결과

본문은 Markdown 문자열이며 제목 없이 저장할 수 있다. [RecordKind](../project/record-types.md)는 여러 개 또는 `[]`를 허용한다. 기본 공개 범위는 `public`이며 실제 공유를 활성화하지 않는다. 사건 시점·완료 상태·감정·검증 상태를 내용에 없는데 추정해 채우지 않는다.

입력 길이, Node 개수, 페이지 크기, 삭제 확인 유효 시간은 [공통 서비스 계약](../architecture/service-contracts.md)의 한도와 기본값을 단일 기준으로 사용한다. 초과 입력을 조용히 자르지 않고 검증 오류를 반환한다. 모델·클라이언트가 `brain_id`, 서버 생성 시각, 삭제 시각, 상태 버전을 임의로 정할 수 없다.

저장 성공 응답은 실제 커밋한 정리본과 ID·revision·상태 버전·검색 상태를 반환한다. 유형을 자동 제안한 경우에도 실제 저장된 값을 보여준다. 저장 후 표시용 본문을 별도의 LLM으로 다시 요약하지 않는다.

기록과 Node의 기본 주제 입력은 선택적인 `concept_hints`다. 서버 내부 에이전트가 같은 brain의 기존 주제를 조회하고 의미에 맞는 연결 또는 새 주제를 제안하며, 실제 ID·참조 검증과 커밋은 도메인 서비스가 수행한다. 본문·색인 작업·주제 연결 작업을 먼저 함께 커밋하고 실제 저장 결과와 `concept_state=pending`을 반환한다. 에이전트 실패·인증 미준비·동명 주제 모호함은 본문 저장 실패가 아니다. 주제 없는 본문 검색도 유지한다.

자동 연결은 저장 요청에 부수된 분류 작업으로만 허용한다. 본문·유형·완료·공개 범위·Node 의미·출처·기록 간 관계를 자동 변경하지 않는다. 연결 변경은 새 메타데이터 revision으로 남기고, 이미 수정·삭제된 대상에는 오래된 작업을 적용하지 않는다. 주제 연결 정정은 명시적 `capture_set_concepts`로 처리하며 기본 저장과 구분한다. 입력·처리·실패·경합 규칙은 [저장 후 주제 연결·청크 규칙](../architecture/ingestion-and-chunking.md)을 따른다.

### 주제 분류 정책

주제는 기록을 다시 찾을 때 재사용할 수 있는 관심사·작업·상황의 범위다. 본문이 실질적으로 다루는 내용에 연결하며 단순한 이름 언급이나 문장별 요약을 주제로 만들지 않는다. 기존 주제는 그 범위가 본문에 맞을 때 재사용한다. 상위·하위·관련 주제를 같은 주제로 축약하지 않고, 별칭은 같은 개념을 부르는 다른 이름에만 사용한다. 기록·세부 항목마다 여러 주제 또는 주제 없는 정상 완료를 허용한다.

하나의 기록도 구별할 필요가 있는 새 범위를 뒷받침할 수 있다. 자동 분류가 제안하는 새 주제에는 무엇을 포함하는지와 필요한 구분을 설명하는 비어 있지 않은 설명을 요구한다. 비슷한 후보의 존재나 유사도 점수만으로 연결·병합하거나 새 주제 생성을 막지 않는다.

같은 brain의 주제가 100개 이하면 전체 주제 목록을 판단에 제공한다. 100개를 넘으면 최대 100개 후보 안에서 현재 연결을 우선하고, 어휘 후보와 이름·설명·별칭의 선택적인 의미 검색 후보를 함께 제공한다. 100개는 전체 목록 제공과 후보 선별을 나누는 실행 상한이며 품질 임계값이 아니다. 의미 검색이 준비되지 않았거나 실패하면 기존 후보 경로로 계속하며, 이를 이유로 본문 저장이나 주제 분류를 차단하지 않는다.

새 주제 제안의 의미 중복 확인은 조건부로 수행한다. 최초 판단에 없던 기존 후보를 찾았을 때만 작업당 최대 한 번 제안 정의를 추가 검토하며 모든 분류에 두 번째 호출을 강제하지 않는다. 같은 개념의 기존 주제 재사용·새 제안 유지·보류 중 판단하고, 원래 본문과 기존 연결은 이 검토로 바꾸지 않는다. 최종 연결은 모델의 범위 판단과 서버 참조·버전 검증을 거친다. 기존 명시적 주제 정정과 오래된 자동 작업의 적용 금지 규칙을 유지하며 기존 기록을 일괄 재분류하지 않는다.

### 조회와 정정

일반 목록은 삭제되지 않은 기록의 현재 revision만 제공한다. 상세 응답은 저장된 Node·주제·출처·재검토 상태를 읽을 수 있게 하며, `node_get`은 부모 기록의 현재 revision에 속한 Node만 직접 조회한다. 과거 Node는 명시적인 Capture 이력 또는 출처 조회에서 해당 저장본과 함께 읽는다.

`source_get`은 SourceRef가 지정한 revision·Node·span을 검증해 정확한 본문 구간과 부모 상세를 반환한다. 과거 저장본은 `is_current=false`로 표시하고 최신 본문으로 바꾸지 않는다. 이력·출처 조회에도 부모 기록의 현재 소유·공개·삭제 경계를 적용한다. 저장 당시 `source`와 안전한 동등성으로 해석한 `resolved_source`를 구분하며, 명시적 과거 조회가 현재 답변의 근거로 사용할 수 있음을 뜻하지는 않는다.

수정·완료 변경·명시적 병합은 기대 revision과 상태 버전을 확인한다. 내용 변경은 새 revision을 만들고 과거 정리본을 변경하지 않는다. 공개 범위만 바꿀 때의 처리, PATCH 생략·null·빈 배열 의미, Node 재검증 및 관계 승계는 공통 계약을 따른다. 기록 안에 완료 여부가 서로 다른 여러 행동이 있으면 하나의 `completion_state`로 모든 행동을 완료했다고 표시하지 않는다.

동일한 request ID와 동일한 요청의 재시도는 같은 커밋을 가리킨다. 같은 ID에 다른 요청은 충돌이며 유사한 본문을 서로 다른 ID로 저장한 경우에는 별도 기록이다.

### 관계 정정

관계 유형은 `related_to`, `clarifies`, `corrects`, `supports`, `contradicts`, `merged_from`, `supersedes`의 7개다. 웹의 생성 선택지와 표시 이름은 [도메인 용어](../project/domain-language.md#관계-유형과-표시-이름)를 따르며 MCP·웹 API·저장 스키마의 값과 일치해야 한다.

관계의 끝점·종류·근거·범위 설명은 생성 후 불변이다. 명시적인 `relation_retract`는 같은 brain의 모든 끝점과 근거 기록의 현재 조회 자격을 확인하고, 비어 있지 않은 이유와 서버 철회 시각을 한 번만 기록한다. 원관계·기록은 보존하지만 철회한 관계는 일반 관계 조회·현재 맥락 해석에서 제외한다. 같은 요청 재시도는 최초 결과를 반환하고 다른 요청으로 이유를 덮어쓰거나 재활성화하지 않는다. 새 관계가 필요하면 별도 ID로 생성한다. 관계 철회에는 기록 삭제 확인 토큰을 사용하지 않는다.

### 출처 재검토

일반 PATCH는 출처를 임의로 제거하는 경로가 아니다. 원출처 변경·삭제로 재검토가 필요한 기록은 그 상태를 상세 응답에 표시한다. 명시적인 출처 재검토 명령은 변경 이유, 기대 버전, 새 본문과 출처를 공통 계약에 따라 검증하고 새 revision을 만든다. 이전 revision에는 당시 본문과 출처 집합을 그대로 보존한다.

참조가 유효하다는 것은 내용이 검증된 사실이라는 뜻이 아니다. 출처를 교체하거나 의존성을 해제했다는 이유로 Node의 사실 검증 상태를 자동으로 승격하지 않는다.

### 삭제

삭제할 대상을 제시하고 사용자에게 다시 확인한 후에만 `deleted_at`을 설정한다. 삭제 확인 토큰·기대 버전·사용자 응답은 같은 대상에 묶이며 모델이 보낸 `confirmed=true`만으로 확인을 대신하지 않는다.

삭제 커밋 뒤 해당 기록·과거 revision·Node는 모든 제품 조회·수정에서 제외한다. 관계·출처를 통해 삭제된 본문·제목을 우회해서 보여주지 않는다. 조회·수정은 `NOT_FOUND`로 처리하며, 성공한 삭제 요청의 동일 재시도에는 내용 없는 최초 삭제 영수증만 반환할 수 있다. 일반 수정으로 `deleted_at`을 비우거나 삭제를 취소할 수 없다.

정본·이력·연결은 내부 저장소에 남기며 제품에 삭제 기록 목록이나 복원 경로를 노출하지 않는다. 검색 작업이 지연되더라도 조회 서비스의 현재 상태 확인으로 즉시 제외한다.

| AC-001 | 제목·유형·Node 없이 유효한 본문만 생성 | 새 기록과 첫 revision이 한 번 저장되고 기본 `public`, `kinds=[]` 및 실제 본문을 반환한다. |

| AC-005 | 여러 기록과 revision이 있는 목록을 필터·페이지로 조회 | 삭제되지 않은 기록의 현재 revision만 반환하고 페이지 규칙·정렬·필터가 일관된다. 미분류 기록도 기본 목록에 포함한다. |
| AC-006 | 과거 revision 또는 정확한 SourceRef를 명시적으로 조회 | 해당 저장본·구간·구조와 현재 여부를 반환하되 현재 부모의 소유·공개·삭제 경계를 적용한다. 최신 본문으로 바꾸지 않으며 일반 목록과 직접 node_get은 과거 revision을 섞지 않는다. |
| AC-007 | 최신 기대 버전으로 수정하거나, 오래된 버전으로 동시에 수정 | 전자는 새 revision·증가한 상태 버전을 생성한다. 단, 일반 수정에서 `visibility`만 바꾸면 revision을 유지하고 상태 버전·색인 세대만 증가한다. 오래된 기대 버전은 `VERSION_CONFLICT`로 변경 없이 종료한다. |
| AC-008 | PATCH에서 필드를 생략하거나 nullable 값에 null·배열에 빈 값을 지정 | 공통 계약의 유지·비우기 의미를 따른다. visibility 생략 시 이전 값을 유지하고 sources의 빈 배열은 의존성을 해제하지 않는다. |
| AC-009 | 명시적으로 완료 상태만 바꾸거나 내용 변경과 함께 바꿈 | 새 revision에 실제 변경을 보존하고 공통 change_kind 규칙을 따른다. 일정·알림이나 본문에 없는 실행 결과를 생성하지 않는다. |
| AC-010 | 같은 request ID를 동일 요청·다른 요청으로 재전송 | 동일 요청은 새 커밋 없이 최초 결과를 참조하고, 다른 요청은 `IDEMPOTENCY_CONFLICT`다. 별도 ID의 유사 메모는 자동 병합하지 않는다. |
| AC-011 | 사용자가 대상과 출처를 지정해 병합 | 대상에만 새 revision을 만들고 출처 기록들은 그대로 둔다. 기대 버전·출처가 유효하지 않으면 일부 병합하지 않는다. |
| AC-012 | 외부 주제 ID 조회 없이 본문·선택적 주제 힌트로 저장 | 본문 저장 뒤 서버가 주제를 찾아 연결하거나 필요한 주제를 생성한다. 동명 후보는 맥락으로 구분하며 모호하면 미연결로 남긴다. 주제 없이 본문만 저장·검색하는 흐름도 유지한다. |
| AC-013 | 유효한 Node 또는 본문 밖 span 제출, 명시적 주제 정정에 다른 revision의 Node·잘못된 Concept ID 제출 | 유효한 구조는 보존하고 잘못된 소속·범위·참조는 거절한다. Unicode code point 기준의 본문 구간을 정확히 읽는다. |
| AC-014 | Node가 있는 본문을 수정하면서 구조를 생략하거나 새 구조를 제출 | 옛 span을 새 본문에 무조건 적용하지 않는다. 공통 `node_status`로 구조 재검토 필요·부재·현재 구조를 구분하고, 유효한 재제출 뒤 Node를 다시 조회할 수 있다. |
| AC-015 | 출처가 정정·삭제되거나 순환·다른 소유 범위 출처를 제출 | 현재 출처 상태를 계산하고 무효한 근거를 사용 가능하다고 반환하지 않는다. 기존 파생 본문은 보존하며 잘못된 새 참조·순환은 거절한다. |
| AC-016 | A1에서 파생한 B를 A2에 맞춰 명시적으로 재검토 | 새 B revision은 검증한 새 출처 집합을 사용하고 옛 B revision에는 A1이 남는다. 이유 없는 빈 출처 교체로 재검토 상태를 우회하지 않는다. |
| AC-017 | 삭제 대상 확인 준비만 호출 | 대상·기대 버전·유효 시간을 담은 preview를 반환하며 기록 내용·삭제 상태는 바꾸지 않는다. |
| AC-018 | 삭제 확인을 취소하거나 토큰이 만료·재사용·버전 충돌·확인 수단 미지원 | 새 삭제를 실행하지 않는다. 모델의 boolean이나 토큰 소지만으로 사람의 확인을 통과하지 않는다. 성공 요청의 멱등 재시도는 AC-021을 따른다. |
| AC-019 | 현재 대상에 대해 실제 사용자 확인 후 삭제 실행 | 같은 트랜잭션에서 `deleted_at`·상태 버전·검색 세대·receipt·토큰 사용·검색 제외 작업을 반영한다. 본문·이력 행은 물리 삭제하지 않는다. |
| AC-020 | 삭제된 기록을 목록·상세·이력·출처·Node·관계 경로로 읽거나 수정·병합·재검토 | 본문·제목·내용 메타데이터를 반환하거나 변경하지 않는다. `include_deleted`·삭제 목록·복원·실행 취소 경로를 제공하지 않는다. |
| AC-021 | 성공한 삭제를 같은 요청으로 재시도하거나 삭제 전 저장·수정 receipt를 재조회 | 삭제를 재실행하거나 시각·버전을 다시 바꾸지 않는다. 과거 receipt를 통해 삭제된 본문을 재생하거나 기록을 재생성하지 않는다. |
| AC-022 | 다른 brain의 ID·클라이언트 주장 소유권으로 생성·참조·조회·수정 | 서버가 정한 소유 범위를 유지하고 참조·접근을 거절한다. 다른 소유자의 존재나 내용을 상세 노출하지 않는다. |
| AC-023 | 커밋 중 오류·응답 유실·색인 처리 지연·늦은 색인 작업 발생 | 정본과 outbox·receipt는 함께 커밋되거나 함께 취소된다. 저장 성공과 검색 준비 상태를 구분하며 삭제된 기록을 늦은 작업이 재게시하지 못한다. |
| AC-024 | 같은 동작을 MCP와 웹 API에서 각각 실행 | 같은 저장 의미·필수값·오류·삭제 확인을 적용하고 실제 커밋 결과를 반환한다. MCP 실패는 도구 오류로 전달하며 실제 Codex 왕복을 검증한다. |
| AC-025 | 내용이 유지된 유형·주제 수정 또는 명시적인 조건 변경 관계 입력 | 공통 안전 승계 기준을 충족하는 관계만 이어가고 실제 내용 변경은 재검토한다. `supersedes`는 새 조건→옛 조건의 범위·근거를 보존하며 단순 최신 시각으로 생성하지 않는다. |
| AC-026 | 관계를 명시적으로 철회하거나 동일·상이 요청으로 다시 철회 | 조회 자격과 이유를 검증하고 `withdrawn_at`·`withdrawal_reason`을 최초 한 번만 설정한다. 원관계 내용·기록을 보존하고 일반 조회·현재 맥락에서 제외한다. 동일 요청은 최초 결과를 반환하며 이유 덮어쓰기·재활성화·복구는 제공하지 않는다. |
| AC-027 | 주제 연결의 모델 호출 실패·인증 미준비·모호한 후보 | 저장 본문·첫 응답을 유지하고 주제 상태와 오류를 따로 표시한다. 재시도는 같은 작업을 사용하며 중복 주제·revision을 만들지 않는다. |
| AC-028 | 주제 연결 중 본문 수정·삭제·명시적 주제 정정 또는 동일 작업 중복 실행 | 기대 버전이 다른 결과는 적용하지 않는다. 성공한 연결만 한 번 새 revision·상태 버전·검색 작업에 반영하며 재귀적인 자동 연결을 만들지 않는다. Node 주제를 기록 전체에 자동 복제하지 않는다. |
| AC-029 | `capture_set_concepts`로 주제 연결을 정정하거나 비움 | 조회 가능한 ID와 기대 버전을 확인하고 새 revision으로 보존한다. 진행 중 옛 자동 작업이 덮어쓰지 못하며 본문·Node 의미·출처·공개 범위는 유지한다. |
| AC-030 | 웹에서 관계 유형을 선택하거나 MCP·웹 API로 만든 관계를 표시 | 선택지는 서버의 7개 유형과 일치하며 `clarifies`를 포함한 모든 유형에 표준 표시 이름을 제공한다. 지원하지 않는 `explains`·`applies_to`를 생성 선택지에 노출하지 않는다. |
| AC-031 | 본문이 실질적으로 다루는 내용·단순 언급·관련되지만 범위가 다른 기존 주제가 함께 있음 | 실질적인 내용과 범위가 맞는 주제를 선택하며 단순 언급으로 연결하지 않는다. 여러 주제·미연결을 허용하고 상위·하위·관련 주제를 별칭으로 합치지 않는다. |
| AC-032 | 한 기록에서 구별되는 새 주제 범위가 제안됨 | 기록 수만으로 생성을 막지 않으며 자동 생성 제안에 비어 있지 않은 범위 설명을 요구한다. 점수만으로 연결·병합하거나 생성을 거부하지 않는다. |
| AC-033 | 주제 100개 이하·초과 또는 의미 후보 검색 미준비·실패 | 100개 이하는 전체 목록을 제공하고 초과 시 최대 100개 후보 안에서 현재 연결을 우선하며 어휘·선택적 의미 후보를 함께 제공한다. 의미 검색 실패에도 기존 후보로 분류를 계속하고 저장 본문을 유지한다. |
| AC-034 | 새 주제 제안 확인에서 최초 판단에 없던 기존 후보를 발견하거나 추가 후보가 없음 | 새로운 후보가 있을 때만 제안 정의의 추가 모델 검토를 작업당 최대 한 번 수행한다. 원래 본문·기존 연결을 재판단하지 않으며 최종 반영에도 명시적 정정·revision·상태 버전 검증을 적용한다. |

## 검증과 지원 범위

계약 검사는 [백엔드 테스트](../../backend/tests)와 [검사 가이드](../guides/testing.md)를 따른다. 삭제 확인을 지원하지 않는 클라이언트에서는 삭제를 차단한다. 자동 계약 검사는 실제 클라이언트의 확인 UI나 모든 운영체제 지원을 증명하지 않는다. 운영체제별 지원과 미검증 사항은 [플랫폼 문서](../architecture/platform-support.md)에서 관리한다.
