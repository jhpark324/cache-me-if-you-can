# 기록 관리 설계

관련 명세: [spec.md](spec.md)

## 구현 개요

FastAPI와 MCP 도구가 같은 도메인 서비스를 호출하고 SQLite에 정본을 저장한다. MCP 어댑터가 내부 웹 API를 재호출하거나 웹 API가 자기 MCP에 연결하는 구조로 만들지 않는다. 저장 시 모델 호출은 필수 단계가 아니다.

서버의 주제 연결은 본문 저장 후 별도 작업으로 실행한다. 일반 입력의 `concept_hints`와 실제 FK 연결을 구분하고, 내부 LangGraph 판단·일반 후보 조회·트랜잭션 검증 책임을 [주제 연결 계약](../../architecture/ingestion-and-chunking.md)에 따라 나눈다. 이 작업은 저장을 실패시키지 않으며 본문·Node 의미·출처를 자동 수정하지 않는다.

구현할 데이터 필드·FK·상태는 [데이터 스키마](../../architecture/data-schema.md), 공통 DTO·도구·경로·한도·오류는 [서비스 계약](../../architecture/service-contracts.md)을 따른다. 이 문서는 기능 내부의 처리 순서와 검증 책임을 정한다. 현재 구현과 검증 결과는 [검증 기록](validation.md)을 따른다.

## 변경 처리 순서

1. 서버 실행 맥락에서 brain·호출자를 결정하고 요청의 형식과 크기를 검증한다.
2. `(principal_scope, request_id)`의 receipt와 요청 fingerprint를 확인한다. 동일 요청의 재시도는 현재 조회 경계를 확인한 뒤 최초 커밋 결과를 참조한다. 같은 ID·다른 입력은 충돌이다.
3. 새 변경이면 같은 SQLite 트랜잭션 안에서 대상 존재·`deleted_at IS NULL`·해당 명령의 기대 버전 또는 최초 변경 조건·참조의 소속과 상태를 확인한다.
4. 해당 명령에 필요한 새 revision·메타데이터·상태 버전과 검색 세대를 기록한다. 출처 재검토는 새 revision의 전체 출처 집합을 교체하며 과거 revision은 수정하지 않는다. 관계 철회는 Capture revision을 만들지 않고 아직 철회하지 않은 관계의 철회 정보만 기록한다.
5. 관련 검색 작업, 필요한 주제 연결 작업과 receipt를 같은 트랜잭션에서 기록하고 커밋한다. 중간 오류는 모두 롤백한다.
6. 커밋한 저장본으로 응답을 구성한다. 저장 성공을 별도 요약이나 모델 응답으로 대신하지 않는다.

모델 추론·색인 반영·사용자 확인을 기다리는 동안 SQLite 쓰기 트랜잭션을 열어 두지 않는다. 응답을 보내기 전에도 현재 삭제·소유 경계를 확인해 동시 삭제된 내용을 재노출하지 않는다.

주제 작업은 최초 저장 receipt와 별도로 요청/반영 revision을 추적한다. 주제만 바뀌면 `concept_enrichment/system` revision과 상태 버전·검색 세대·완료 기록을 함께 반영한다. 변경이 없으면 revision을 추가하지 않는다. 명시적 `capture_set_concepts`는 일반 `edit` revision으로 연결을 교체하고 자동 재분류를 시작하지 않는다. 삭제·수정·정정 후 늦은 작업, 모델 장애와 인증 미준비는 계약의 실패·superseded 규칙을 따른다. 본문 색인은 주제 작업의 성공을 기다리지 않는다.

## 조회와 구조화 정보

- 목록은 현재 기록의 요약·버전·검색 상태만 제공한다. 공통 커서 정렬을 사용하고 과거 revision과 삭제된 기록을 제외한다.
- 상세는 저장된 본문·유형·주제·Node·출처·재검토 상태를 반환한다. 출처가 삭제되었으면 내용 없는 참조와 상태만 필요한 범위에서 표시하고 삭제된 제목·본문을 따라 읽지 않는다.
- `node_get`은 현재 revision에 속한 Node의 부모 기록·구간 조회 자격을 확인한 뒤 본문에서 읽는다. 과거 Node는 명시적인 Capture 이력 또는 출처 상세에서 해당 저장본과 함께 조회하며 오래된 Node ID를 새 Node로 치환하지 않는다. Node 자체에 독립 원문이나 별도 수정 경로를 만들지 않는다.
- `source_get`은 공통 SourceRef의 capture/revision/Node 소속과 span을 검증해 SourceDetail을 구성한다. 저장 당시 `source`와 동등성을 판정한 `resolved_source`를 구분하고, 지정한 저장본·구간의 본문을 그대로 반환한다. 과거 revision은 현재 여부를 표시하며 최신 본문으로 대체하지 않는다.
- 이력·출처 조회는 지정한 revision을 읽되 부모 기록의 현재 조회 자격을 적용한다. 부모 삭제 후에는 오른쪽 출처 패널에서 다시 요청하더라도 내용 없는 `NOT_FOUND`다. 현재 문맥에 적용할 자료를 찾는 자동 검색의 기본값과는 구분한다.
- 주제 이름과 별칭은 ID를 찾는 수단이며, 동명이 항목을 이름만으로 자동 합치지 않는다. Node별 주제와 기록 전체 주제를 각각 보존한다.

검색 기반 단일턴 응답과 오른쪽 출처 패널의 화면 구현은 후속 기능이다. 002는 그 화면이 호출할 조회 계약까지 제공하며 웹 채팅·후속 대화 상태를 저장하지 않는다.

## Node·관계·출처의 수정

본문 수정 후 기존 span을 그대로 사용하는 것은 금지한다. 재제출한 Node는 새 본문의 범위로 검증하고, 생략한 구조는 공통 `node_status` 규칙으로 재검토 필요 여부를 드러낸다. 구조 검증 완료는 사실 검증 완료를 뜻하지 않는다.

본문과 의미가 유지된 수정은 공통 안전 승계 조건을 충족할 때에만 출처·관계를 이어간다. 실제 의미 변경에서는 단순한 문자열 유사도나 Node 순번만으로 과거 근거를 최신으로 바꾸지 않는다. 새 revision의 Node ID가 달라지는 경우에는 동일성을 확인한 복제 매핑을 사용한다.

관계의 끝점·종류·근거·설명은 불변이며 정정은 `relation_retract`로 처리한다. 요청 ID와 관계 ID로 중복을 확인하고 모든 끝점·근거의 현재 조회 자격을 검사한 뒤, `withdrawn_at IS NULL`인 행의 시각·비어 있지 않은 이유와 receipt를 원자적으로 기록한다. 별도 관계 버전이나 기록 삭제 토큰은 요구하지 않는다. 같은 성공 요청은 최초 결과를 반환하고 후속 요청으로 이유를 덮어쓰지 않는다. 철회한 관계는 일반 관계 조회·현재 맥락 해석에서 제외하며 복구 동작은 두지 않는다.

출처를 다시 검토하는 동작은 일반 PATCH와 구분한다. 새 본문·출처·이유·기대 버전을 한 트랜잭션으로 처리하고, 새 참조의 유효성·의존 관계를 확인한다. 잘못된 출처를 지웠다는 이유로 내용을 독립된 검증 사실로 자동 승격하지 않는다.

## 삭제 확인과 소프트 삭제

삭제는 준비와 실행 두 단계다. 준비 단계는 현재 대상과 미리보기·기대 버전·만료 시각을 제공하며 정본을 바꾸지 않는다. 실행 단계는 실제 사용자 응답을 확인한 뒤 짧은 트랜잭션에서 현재 대상·토큰·기대 버전을 다시 확인한다.

삭제 커밋은 `deleted_at` 설정, 상태 버전·검색 세대 갱신, 토큰 사용 처리, 삭제 receipt, 검색용 제거 작업을 함께 저장한다. 정본·이력은 내부 보존하되 이후 제품 상세·이력·Node·수정·병합·재검토 경로에서 접근하지 못한다.

`deleted_at`을 비우는 코드 경로, 삭제 기록 필터, 복원·실행 취소 endpoint는 구현 범위에 없다. 성공한 삭제의 동일 재시도에는 최초 커밋을 나타내는 내용 없는 `DeleteResult`를 반환하며, 과거 생성·수정 receipt로 삭제 본문을 재생하지 않는다.

MCP의 실제 사용자 확인 기능은 설치한 SDK와 Codex를 대상으로 왕복 검증한다. 지원되지 않으면 오류로 종료하고 삭제하지 않는다. 웹 확인도 모델이 만들어낸 인수가 아니라 사용자의 명시적 조작에 연결한다.

## 오류·경계 조건

- 같은 버전을 편집한 두 요청 중 하나만 커밋된다. 뒤 요청은 자동 덮어쓰기 없이 충돌로 처리한다.
- 삭제 준비와 실행 사이의 수정·삭제는 기존 토큰으로 실행할 수 없게 한다.
- 요청 형식 오류·초과 길이·잘못된 참조는 쓰기 전에 거절하고, 트랜잭션 내부에서 발견한 충돌은 전체 롤백한다.
- 이미 커밋한 요청은 응답 유실 뒤 재시도해도 중복 revision·작업을 만들지 않는다.
- 오래된 색인 행과 후속 작업이 남아 있어도 현재 SQLite의 삭제·revision·세대를 통과하지 못하면 제품 조회에 사용할 수 없다.
- `created_via`는 발화자가 아니고, 저장 시각은 사건 시점이 아니며, 유형은 사실 검증이나 권한이 아니다.

## 결정과 실제 검증이 남은 점

공통 [MCP SDK v2 결정](../../decisions/ADR-005-mcp-python-sdk-v2.md)과 [검색 설계](../../architecture/search-and-embedding.md)를 따른다. 실제 패키지 버전은 `backend/uv.lock`에 고정했으며 검증 환경은 [검증 기록](validation.md)에 남긴다.

미검증 위험은 실제 Codex의 삭제 확인 지원, SQLite FK·트랜잭션·동시성, 두 어댑터의 오류 표현, OS별 파일·프로세스 동작이다. 검사 방법은 [검증 계획](validation.md)에 두며 문서 작성만으로 해소됐다고 표시하지 않는다.
