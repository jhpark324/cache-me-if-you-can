# SDD 작업 절차

## 1. 작업 맥락 찾기

1. `docs/index.md`에서 해당 영역으로 이동한다.
2. 기존 기능이면 `docs/specs/index.md`에서 기능을 찾고 해당 기능의 `index.md`, `spec.md`를 읽는다.
3. 현재 단계에 필요한 설계·작업·검증 문서와 직접 연결된 공통 문서만 추가로 읽는다.

전체 문서나 모든 기능 명세를 미리 읽지 않는다. 코드 탐색은 명세에서 정한 범위와 영향이 있는 경로부터 시작한다.

## 2. 명세 작성

- 새 기능이면 사용하지 않은 번호로 `docs/specs/<번호>-<slug>/`를 만든다.
- [템플릿 인덱스](../templates/index.md)에서 `feature-index.md`를 기능의 `index.md`로 복사하고 `spec.md`를 생성한다.
- 문제, 포함·제외 범위, 관찰 가능한 수용 기준을 작성한다.
- 기능 내부에서 고유한 `AC-001` 형태의 수용 기준 ID를 부여한다. 다른 기능에서 참조할 때는 기능 ID와 함께 적는다.
- 제품 동작을 바꾸는 요청은 관련 명세를 먼저 갱신한다. 불명확한 사항은 미정으로 표시하고 사용자 지시와 확인된 맥락으로 해결한다.
- 대상 기능과 직접 관련된 질문만 확인하고, 이미 정해진 범위 안에서는 작업을 계속한다.

## 3. 설계와 작업 분해

- 구현 방식, 데이터 흐름, 인터페이스, 오류 처리 등 필요한 설계를 `design.md`에 작성한다.
- 여러 기능이 공유하는 구조는 `docs/architecture/`에 기록하고 연결한다.
- 중요한 선택의 대안과 이유는 필요한 경우 ADR로 남긴다.
- 실행할 작업을 `tasks.md`에 `T-001` 형태로 나누고 관련 수용 기준을 연결한다. 준비 작업은 연결할 수용 기준 대신 목적을 적어도 된다.
- 기능 간 순서·의존성·연동 검증 관문은 [작업 계획](../plans/index.md)에 둔다. 기능별 체크리스트와 실행 결과는 해당 `tasks.md`·`validation.md`가 기준이며 전역 계획에 중복 기록하지 않는다.
- 문서 양은 변경 규모에 맞춘다. 작은 수정은 기존 기능 문서를 갱신하며, 새 기능도 별도 설계·작업 문서가 불필요하면 기능 인덱스에 그 이유를 적는다.

## 4. 구현

- 명세의 범위와 수용 기준에 맞춰 구현하고 작업 상태를 갱신한다.
- 구현 중 요구사항이나 설계가 바뀌면 관련 문서를 함께 갱신한다.
- 관련 없는 기능이나 기술 선택을 임의로 추가하지 않는다.

## 5. 검증과 완료

- `validation.md`에 수용 기준별 검증 방법, 실제 결과, 근거를 기록한다.
- 필요한 자동 검사와 수동 확인을 변경의 성격에 맞게 수행한다. 문서 변경은 링크와 내용의 일관성을 확인한다.
- 실행하지 않은 검증은 `미검증`으로 남기며 성공으로 기록하지 않는다.
- 범위 내 수용 기준이 충족되고 근거를 남긴 경우에만 기능 상태를 `verified`로 변경한다.
- 남은 문제나 제약은 기록하고, 기능 인덱스와 `docs/specs/index.md`의 상태를 맞춘다.

## 문서 유지 규칙

- 문서 생성·이동·삭제 시 가장 가까운 `index.md`의 링크를 갱신한다.
- 기능 인덱스에는 실제 생성된 문서만 연결한다. 템플릿의 안내 문구와 자리표시자는 작성 시 정리한다.
- 같은 요구사항이나 결정을 여러 문서에 복제하지 않고 원문을 링크한다.
- 링크는 상대 경로로 작성하고, 기능 간 의존성은 대상 기능의 인덱스나 명세를 연결한다.
- 진행 상태나 문서 작성 단계가 새로운 승인 요구를 만들지는 않는다. 이미 요청된 범위의 작업은 계속 수행한다.
