# 명세 기반 개발

## 시작점

`docs/index.md`에서 작업 영역을 찾고 [현재 기능 명세](../specs/index.md)와 필요한 아키텍처 문서만 읽는다. 모든 명세·연구 자료를 미리 읽지 않는다.

## 변경 순서

1. 해당 명세의 범위와 수용 기준을 확인한다. 제품 동작을 바꾸면 명세를 먼저 갱신한다.
2. 여러 기능에 영향을 주는 구조는 `architecture/`, 중요한 기술 선택의 이유는 `decisions/`에 기록한다. 미정 사항과 구현된 사실을 구분한다.
3. 명세와 관련 코드·테스트를 함께 변경한다. 사용자 기록이나 개인 설정을 시험 데이터로 사용하지 않는다.
4. [검사 가이드](testing.md)에 따라 변경에 필요한 검사를 실행한다. 실행하지 않은 검사는 성공으로 기록하지 않는다.
5. PR에는 실제 변경·검증 명령·결과·남은 한계를 적는다. 일회성 원시 로그·캡처는 CI 산출물이나 체크아웃 밖에 보관한다.

## 문서 규모

작은 변경은 현재 명세에 반영한다. 별도 검토가 필요한 기능은 `docs/specs/<slug>.md` 또는 `docs/specs/<slug>/`에 제안을 작성하고 인덱스에 등록한다. 문제·포함/제외 범위·관찰 가능한 `AC-001` 형태의 수용 기준을 포함한다. 모든 변경마다 설계·작업·검증 문서를 별도로 만들 필요는 없다.

복잡한 기능에는 [템플릿](../templates/index.md)을 선택적으로 사용한다. 제안 상태는 `draft`, 구현 중은 `in-progress`, 범위 내 수용 기준을 확인한 경우는 `verified`로 구분할 수 있다. 문서 상태는 새로운 사용자 승인 절차를 만들지 않는다.

## 문서 유지

문서를 추가·이동·제거하면 가장 가까운 `index.md`와 상대 링크를 갱신한다. 같은 계약을 여러 곳에 복제하지 않는다. 테스트 fixture와 실행에서 생성한 manifest를 구분하고, 코드가 읽는 예제·생성기 경로도 함께 수정한다. [공개 문서 관리](documentation.md)를 따른다.
