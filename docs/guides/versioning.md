# 버전 정책

Cache Me If You Can은 백엔드와 프런트엔드에 같은 제품 버전을 사용한다. `주.부.수` 형식은 [SemVer 2.0.0](https://semver.org/lang/ko/)을 기준으로 한다. `0.x`는 초기 개발 단계이며, 아래의 부·수 버전 구분은 이 프로젝트의 개발 정책이다. `0.x` 전체의 호환성을 보장한다는 뜻은 아니다.

## 버전을 올리는 기준

| 변경 | 개발 단계 `0.x` | 안정화 이후 `1.0.0` 이상 |
| --- | --- | --- |
| 기존 계약을 유지하는 버그 수정 | 수 버전: `0.2.0 → 0.2.1` | 수 버전: `1.2.0 → 1.2.1` |
| 기능 추가·사용자에게 의미 있는 개선 | 부 버전: `0.2.0 → 0.3.0` | 호환되면 부 버전: `1.2.0 → 1.3.0` |
| 기존 계약과 호환되지 않는 변경 | 부 버전: `0.2.0 → 0.3.0` | 주 버전: `1.2.0 → 2.0.0` |
| 실행 산출물·계약이 같은 문서·테스트만의 변경 | 제품 버전을 올리지 않음 | 제품 버전을 올리지 않음 |

상위 숫자를 올릴 때 하위 숫자는 `0`으로 시작한다. 안정화 이후 공개 계약의 사용 중단을 예고하는 변경은 부 버전에 포함하고, 실제 제거는 주 버전에서 처리한다. 예를 들어 실행 명령·환경 변수·기본 데이터 경로를 새 이름으로 바꾸고 이전 이름 지원을 제거하는 개발 변경은 `0.1.0 → 0.2.0`에 해당한다.

## 호환성을 판단하는 범위

호환성은 소스 코드의 함수뿐 아니라 사용자가 실행·연결·보관하는 계약을 포함한다.

- 웹 API와 MCP의 도구 이름, 입출력 필드, 오류와 동작 의미.
- 실행 명령, 옵션, 환경 변수, 설치 설정과 기본 데이터 경로.
- 저장 파일명·형식과 백업·복원 절차. 스키마가 같더라도 경로나 파일명을 바꾸어 수동 작업이 필요하면 호환 변경으로 보지 않는다.

구체적인 계약은 [현재 명세](../specs/index.md)와 [명명 규칙](../project/domain-language.md#제품-이름과-실행-식별자)을 따른다. 제품 버전은 DB migration, DTO의 `schema_version`, 기록의 상태 버전, MCP 프로토콜 버전과 별개다. 제품 버전을 올렸다는 이유만으로 이 버전들을 함께 올리지 않는다.

## 변경 묶음과 버전 파일

각 커밋마다 버전을 올리지 않는다. 검증해 전달할 변경 묶음을 정하고, 그 묶음에서 가장 큰 호환성 변화에 맞춰 한 번 정한다. 변경 이유와 필요한 사용자 조치를 PR이나 릴리스 설명에 남긴다.

제품 버전은 [백엔드 설정](../../backend/pyproject.toml)의 `project.version`과 [웹 설정](../../frontend/package.json)의 `version`을 함께 갱신한다. [백엔드 lock](../../backend/uv.lock)의 자체 패키지 버전과 [웹 lock](../../frontend/package-lock.json)의 루트 버전도 일치시킨다. 버전 변경만을 위해 의존성을 업그레이드하지 않는다.

실행 중인 웹 API·건강 응답·MCP 서버 정보·백업 manifest의 제품 버전은 설치된 `cache-me` 배포 패키지의 메타데이터에서 읽는다. 소스에 별도의 버전 상수를 두지 않으며, 소스 버전을 변경한 뒤에는 `setup` 또는 잠금 파일을 따르는 `uv sync`로 실행 환경의 패키지 메타데이터도 갱신한다.

이미 배포한 버전의 산출물이나 공개한 태그를 덮어쓰지 않는다. 배포 내용에 수정이 필요하면 새 버전을 사용한다. 태그를 사용할 때의 `v`는 태그 접두어이며, 패키지 버전에는 `v`를 붙이지 않는다.

## `1.0.0`의 기준

핵심 사용자 흐름과 공개 계약을 안정화하고, 지원한다고 선언할 운영체제에서 설치·업데이트·백업 및 복원을 검증한 뒤 `1.0.0`으로 전환한다. 이때 지원 환경, 호환성 범위, 변경·사용 중단 정책을 문서로 명시한다. 복원 UI가 없더라도 지원하는 복원 절차는 재현 가능해야 한다. 기능 수나 개발 기간만으로 안정판을 선언하지 않는다.
