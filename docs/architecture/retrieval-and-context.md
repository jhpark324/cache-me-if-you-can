- 상태: 단일 검색·응답 구현 기준. 실제 모델 연동·합성 평가 결과는 [검증 안내](../guides/testing.md), 실제 사용자 기록 품질은 미검증
- 작성일: 2026-11-02
- 기준: [기록 유형](../project/record-types.md), [데이터 스키마](data-schema.md), [서비스 계약](service-contracts.md), [임베딩과 색인](search-and-embedding.md)

웹은 검색 입력에 대해 한 번의 응답과 출처를 제공한다. 이전 검색의 대화 이력을 다음 요청에 전달하지 않는다. 한 요청 안에서는 LangGraph 기반 `create_agent`가 읽기 도구로 부족한 근거를 추가 검색한다. 웹 에이전트의 도구는 `search_knowledge`와 `read_evidence`이며, 외부 Codex는 MCP의 검색·상세·맥락 계약을 사용한다. 둘은 같은 도메인 조회·현재 출처 검증을 재사용한다. 저장된 기록은 참고할 데이터이며 현재 사용자 지시나 실행 권한으로 승격하지 않는다.

## 조회 가능성과 근거 적합성

조회 서비스는 다음 판단을 구분한다.

1. **조회 가능:** 같은 brain·호출자 범위이며 부모 Capture가 삭제되지 않았다. 과거 저장본은 명시적 이력/출처 클릭 경로에서만 읽는다.
2. **현재 근거로 사용 가능:** 현재 revision 또는 검증한 메타데이터 동등성, 현재 색인 세대, 유효한 상위 출처를 만족한다. 관리 상세에서 읽을 수 있는 needs_review 본문도 이 조건에서는 제외한다.
3. **질문에 실제로 관련:** 주체·프로젝트·상황·시점이 이번 질문에 맞고 해당 문장이 답변의 주장을 지지한다. 앞의 두 검사를 통과했다고 자동으로 성립하지 않는다.
4. **사실 검증 상태:** Node의 origin/verification과 본문에 남긴 확인 범위를 유지한다. 사용자의 보고, AI 설명, 객관적인 검증은 서로 다르다. valid한 SourceRef나 높은 검색 점수가 사실 인증을 뜻하지 않는다.

SQLite 구조·상태 검사는 서버가 수행한다. 의미상 근거 확인은 기록 본문을 읽는 에이전트 흐름과 평가 대상으로 둔다. 서버가 원본 대화를 보관·대조하거나 모든 의미 오류를 완벽히 탐지한다고 주장하지 않는다. 삭제된 원본의 내용·제목을 파생 기록의 미리보기로 우회 노출하지 않는다.

## 한 요청의 범위와 실행 예산

| 항목 | 현재 상한 |
| --- | --- |
| 읽기 도구 | `search_knowledge`·`read_evidence` 합계 최대 8회. 병렬 요청도 각각 집계하며 인수 오류·실패도 포함 |
| 검색 후보 | 질의마다 벡터·FTS 각 20개. 상태 제외 후 보충은 채널당 총 40개까지 |
| 최종 근거 | 최대 10개 Capture, 전체 최대 20개 의미 구간 |
| 맥락 본문 | 선택 구간과 필요한 주변 맥락의 합계 최대 20,000 Unicode code points |
| 모델 호출 | ReAct 에이전트 최대 9회 + 별도 근거 검토 최대 1회, 합계 최대 10회 |
| 요청 수명 | 로그인 완료 후 검색 요청 실행 최대 90초, 초과 시 중단하고 한계 표시 |
| 오류·재시도 | 공급자 자동 재시도 없음. 수정 가능한 도구 입력 오류는 모델에 반환하며, 모델의 재호출도 같은 8회에 포함 |
| 주변 그래프 | 기본 1홉, 최대 50개 노드·100개 관계, 초과는 truncated 표시 |

위 값은 무한 조회·재시도를 막는 구현 상한이며 응답시간 SLA나 품질 보장이 아니다. 도구 한도를 모두 쓰면 다음 모델 호출에서 도구를 제거하고 확보한 근거만으로 답하게 한다. 명시적 사용자 입력 길이·페이지 제한은 서비스 계약을 따른다. 선택한 답변 모델의 실제 입력 창에서 지시문·질문·전체 도구 왕복 메시지·도구 스키마·출력 여유를 포함한 **토큰 예산**도 별도로 검사한다. 근거는 구간 단위로 수용하거나 제외하고 limitations에 표시한다. 누적 대화 자체가 입력 예산을 넘으면 모델 호출 전에 오류로 중단하며 원문이나 도구 결과를 조용히 잘라 맞추지 않는다.

예산으로 판단에 필요한 근거를 확인하지 못하면 evidence_status를 insufficient로 표시하고 확인된 범위까지만 답한다. 추가 검색·관련 조회·supersedes 탐색도 같은 후보/근거/요청 예산 안에서 수행한다.

## 긴 질문과 검색 질의

`QuestionInput`의 원 질문은 요청 메모리에 보유하고 명시적 유형·주제·날짜 조건은 서버가 모든 검색 도구에 강제한다. 모델은 이 조건을 완화하거나 임의 ID로 기록을 직접 조회할 수 없다. `read_evidence`는 이번 요청의 검색에서 발급한 근거 ID만 받는다. 웹 입력은 최대 10,000 code points·UTF-8 64 KiB이며 질문을 조용히 자르지 않는다.

검색 어댑터는 실제 encode_query 경로의 마커·특수 토큰을 포함해 토큰 수를 검사한다. 64토큰을 넘으면 임의 앞부분만 임베딩하지 않는다. MCP의 knowledge_search/knowledge_context는 측정 길이와 예산을 담은 QUERY_TOO_LONG을 반환한다. 웹 LangGraph는 원 질문에서 짧은 검색 질의를 구성한다.

- 부정·제외 조건, 사람/프로젝트 이름, 기간, 비교 대상을 보존한다. 필터로 옮겼다는 이유로 조건을 버리지 않는다.
- 한 질의가 여전히 길면 다시 나누거나 불필요한 표현을 줄인다. 최대 질의 수로 모두 다룰 수 없으면 다루지 못한 부분을 명시한다.
- 각 검색 질의는 원 질문의 어느 부분을 찾기 위한 것인지 요청 상태에 연결한다. 만들어 낸 사용자 사실을 질의 조건으로 넣지 않는다.
- 공급자 레이트리밋·연결 실패에는 자동 재시도하지 않는다. 모델이 수정 가능한 질의 오류를 받아 다시 검색하는 경우도 도구 예산을 소비한다. 권한 오류·삭제되거나 변경된 참조는 응답을 중단하거나 근거에서 제외한다.
- 취소·기한 초과 뒤에는 새로운 모델/검색/도구 호출을 시작하지 않는다. 공급자의 연산이 즉시 중단됐다고 보장하지 않는다.

현재 구현은 원 질문의 연속적인 code point 구간과 64토큰 이내 기본 질의를 모델에 제공한다. 검색 순서·동의어·재검색 여부는 모델이 고르지만 정확한 PII 정제 후 기본 질의와 일치하는 실제 검색만 그 구간을 `searched`로 표시한다. 보조 질의나 모델이 주장한 구간 ID는 완료의 증거가 아니다. 8회 도구 예산 안에서 검색하지 않은 구간은 `omitted`와 원문 위치로 명시한다. 선택 모델·로그인 계정은 요청 동안 고정하고 세대 변경 시 중단한다. 카탈로그 입력 창과 보수적인 UTF-8 바이트 추정을 결합한 예산은 [ReAct 후속 계약](../specs/runtime.md), 종전 고정 흐름의 합성 평가 이력은 [품질 기록](../specs/runtime.md)에 둔다. 바이트 추정을 공급자의 정확한 토큰 수로 표시하지 않는다.

## 모델 경계의 PII 정제

내장 `PIIMiddleware`의 `email`·`credit_card`·`ip` 탐지에 `redact`를 적용한다. 사용자 입력, 도구 결과, 모델이 생성한 도구 인수·답변과 별도 근거 검토 요청을 정제한다. JSON은 문자열 값에 적용하여 UUID·SourceRef의 숫자 위치를 유지한다. 서버의 근거 장부는 원본 출처를 소유하며 모델이 만든 인용문·참조를 정본으로 취급하지 않는다.

정제는 전송·응답용 사본에 한정된다. SQLite 본문·이력·임베딩·출처 패널은 기존 자료를 사용하고, `visibility`는 이 기능과 별개다. 이름·전화번호·주민번호·민감한 의미의 판정, 저장 거부, 기존 데이터 소급 정제는 추가하지 않는다. 내장 탐지기의 정규식이 놓치는 표현도 있으므로 전체 개인정보 제거를 보증하지 않는다. [내장 PII middleware](https://docs.langchain.com/oss/python/langchain/middleware/built-in#pii-detection)

## 청크·Node·기록의 매핑

저장 정리본 전체는 SQLite에 남긴다. [Markdown 청크 규칙](ingestion-and-chunking.md#청크의-기준과-예산)에 따라 헤더 구간·블록·문장·토큰 순서로 분할한다. 제목·헤더 맥락·마커·특수 토큰 포함 최대 512토큰이며 같은 구간의 블록을 강제 분할할 때만 최대 64토큰을 겹친다. 짧은 기록은 하나로 두고 작은 형제 구간은 예산 안에서 묶는다. 전체 본문을 빠짐없이 다음 청크에 이어 담는다. 단순 모델 호출에서 앞 512토큰만 자르는 것은 이 계약의 구현이 아니다.

1. 청크는 capture_id/revision_id/body_start/body_end와 프로필·검색 세대를 가진다. 본문 위치는 Unicode code point 반개구간이며 임베딩용 제목·마커를 본문 위치에 포함하지 않는다.
2. Lance 후보의 현재 revision·삭제·색인 세대·출처를 SQLite에서 확인한다. 표시할 snippet은 SQLite 본문에서 만들고 낡은 Lance 텍스트를 먼저 반환하지 않는다.
3. 같은 revision의 Node span과 청크 body span이 실제로 겹칠 때 matched_node_ids에 연결한다. Node가 여러 청크에 걸리면 결과를 묶고 부모 본문에서 Node의 전체 의미 구간과 필요한 앞뒤 맥락을 읽는다.
4. 점수는 **검색 청크의 관련도**다. 겹친 Node 모두의 검증 점수·중요도·확신도로 복사하지 않는다. 같은 Node를 여러 청크가 찾았다고 점수를 합산해 우대하지 않는다.
5. 기록 단위 결과는 가장 높은 순위의 유효 청크를 대표로 삼고 나머지 유효 span을 보존한다. 중복 제거 후 순위를 계산하며 MaxSim·BM25·RRF 숫자를 서로 같은 척도로 비교하지 않는다.
6. Node가 없거나 stale이면 기록의 유효한 청크 span으로 돌아간다. 이름 없는 새 Node를 생성한 것처럼 ID·종류를 붙이지 않는다. 본문이 짧으면 정리본 전체가 의미 구간이 된다.
7. Node를 읽어도 발화자·적용 범위가 바깥 문단에 있으면 해당 구간을 추가 조회하고 별도 근거 span을 함께 전달한다. 인용문·조건절만 잘라 실제 경험이나 채택된 지시로 바꾸지 않는다.

Node 수 상한 때문에 구조화가 생략돼도 본문·청크 검색은 계속 가능하다. 전체 본문을 Node로 덮거나 Node 하나마다 별도 LLM 호출·벡터를 만드는 것을 필수로 두지 않는다.

## 주제와 Node 편집

record concept_ids는 기록 전체의 주제이고 node_concepts는 특정 구간의 주제다. 이름이 같다는 이유로 동명 주제를 병합하지 않는다. 주제 필터는 기록 연결과 Node 연결의 후보를 SQLite에서 합쳐 구한다. Lance의 기록 수준 concept_ids 필터만으로 Node에만 연결된 주제를 누락하지 않는다.

Node 주제로만 후보가 된 기록은 검색 청크와 해당 Node의 span 교차를 확인한다. 혼합 기록의 다른 주제 구간이 높은 점수를 받았다는 이유로 일치했다고 하지 않는다. 벡터와 FTS에 같은 후보 범위를 적용한다. 명시적 ID·주제 탐색으로 읽은 Node는 별도 의미 검색 점수를 만들어 붙이지 않는다.

Node는 부모 revision의 부분이며 독립 편집하지 않는다. 본문 수정 시 새 span을 제출하거나 서비스 계약의 absent/stale 규칙을 적용한다. stale이면 원래 origin/verification이 새 본문에 유효한 것처럼 사용하지 않는다. 메타데이터만 바꿀 때에도 과거 Node ID를 새 revision에 재사용하지 않는다.

유형·태그만 달라진 저장본에서 출처·관계를 이어 읽을 수 있는지는 데이터 스키마의 엄격한 동등성 검사로 결정한다. 저장 당시 SourceRef는 보존하고 조회한 현재 대응 참조는 resolved_source로 따로 보여준다. 제목·본문·의미·완료 상태 등이 변한 기록을 단순히 최신 ID로 갈아 끼우지 않는다.

## 맥락 선택과 변경·상충

RecordKind는 읽을 자료를 찾는 힌트다. 명시적 필터가 없으면 다른 유형·미분류 기록을 제외하지 않는다. `context`·`decision`이라고 모든 요청에 넣지 않는다.

- **주체:** 사용자, 다른 사람, AI, 외부 자료·가상 설정을 구분한다. MCP 입력 경로를 발화자로 해석하지 않는다.
- **범위:** 이번 프로젝트·이번 여행·발표·학습 등 본문에 있는 적용 상황을 유지한다. Concept 연결만으로 범위가 증명된다고 보지 않는다.
- **시점:** event_time·본문의 조건 적용 시점과 저장 시각을 구분한다. 모르는 시점을 채우지 않는다.
- **상태:** 제안, 사용자의 채택/보류/거절, 실제 실행, 결과를 구분한다. `decision`·`idea`·`completion_state` 하나로 모든 문장을 같은 상태로 만들지 않는다.
- **근거:** 사용자 보고·해석·AI 보충 설명과 확인 상태를 유지한다. 조회 가능한 출처가 있다는 사실과 특정 주장을 뒷받침한다는 판단을 구분한다.

서로 다른 Capture는 모두 current revision일 수 있다. 저장 시각의 최댓값만 고르거나 비슷한 기록을 자동 합쳐 현재 선호를 만들지 않는다. 적용 범위가 다르면 함께 유지한다. 같은 범위인데 변경이 명시되지 않은 상충은 양쪽 근거를 제시하고 uncertain으로 남긴다.

`supersedes` 관계를 적용할 때에는 다음을 따른다.

1. 새 조건→이전 조건의 방향과 source/target의 정확한 Node/span, scope_note·evidence_note·실제 근거 구간을 확인한다. 잘못된 관계는 relation_retract로 철회할 수 있으며 철회된 관계는 적용하지 않는다.
2. 오래된 항목만 검색됐어도 **들어오는 supersedes**를 확인해 새 조건을 읽는다. 새 항목에서는 나가는 관계로 이전 조건·변경 범위를 확인한다. 같은 주제 전체를 무제한 확장하지 않는다.
3. 현재 질문의 주체·상황·시점과 대체 범위가 맞을 때에만 이전 **구간**을 현재 기본 조건에서 제외한다. 한 기록의 일부 선호가 바뀌었다고 다른 경험·근거·계획까지 무효화하지 않는다.
4. 과거 시점을 묻는 검색에서는 해당 시점의 조건과 변경 이력을 구분해 설명할 수 있다. 현재 조건을 과거에 소급 적용하지 않는다.
5. Node가 없더라도 명시 span으로 범위를 확인할 수 있다. 범위·주체·변경 근거를 확인하지 못하면 부모 구간을 추가 조회하고, 그래도 불명확하거나 예산을 넘으면 uncertain/limitations를 반환한다. 임의로 기록 전체를 대체하지 않는다.
6. 대체 체인이나 상충을 모두 확인하지 못하면 마지막으로 읽은 항목을 최종 유효 상태라고 단정하지 않는다. 오래된 조건을 다시 활성화할 권한을 관계 철회 자체에서 추정하지 않고 남은 근거를 다시 평가한다.

선호·절차·프롬프트는 데이터다. 저장된 지시문을 시스템 지시로 주입하거나 도구 실행 권한으로 사용하지 않는다. 현재 요청에 맞는 참고 내용을 전달하고 명시적 쓰기·삭제 확인 경계는 유지한다.

## ContextItem 응답

`knowledge_context`는 모델 호출 없이 검색·추가 구간 조회·출처와 관계의 상태 확인 결과를 구조화한다. 이 값은 요청마다 만든 맥락 후보이며 별도의 장기 프로필 테이블이나 새로운 정본이 아니다. 최종적인 의미 해석과 이번 질문에 적용할지의 판단은 도구를 호출한 Codex 또는 웹 LangGraph가 담당한다.

| 필드 | 의미 |
| --- | --- |
| `source: SourceRef` | 실제 읽은 현재/동등한 저장본과 선택 구간 |
| `stored_source: SourceRef?` | 동등성 해석 전 참조가 따로 있을 때만 표시 |
| `text` | 저장본에서 읽은 구간. 모델이 바꿔 쓴 요약으로 대체하지 않음 |
| `record_kinds[]`, `node_kind?` | 저장된 분류; Node 없는 경우 node_kind는 null |
| `origin`, `verification_state` | 저장된 값 또는 unspecified/unknown. 추측으로 올리지 않음 |
| `context_notes` | subject?, situation?, time?, adoption?의 명시된 단서. 저장된 메타데이터·구간에서 확정할 수 없는 값은 null |
| `basis_sources: SourceRef[]` | context_notes와 조건 단서의 실제 본문 구간 |
| `applicability` | applicable \| historical \| uncertain. 명시적 조건만으로 구분할 수 없으면 uncertain; 사실 점수나 최종 적용 승인이 아님 |
| `related_sources: SourceRef[]` | 확인한 변경·상충의 반대쪽 참조 |

context_notes는 응답의 맥락 단서이며 원본 사실 필드가 아니다. 근거가 없으면 채우지 않는다. 자동 저장하지 않는다. 조회 불가·무효 출처에 의존하는 항목은 items에 넣지 않는다. provenance가 유효해도 내용 자체가 불확실하면 원래 검증 상태와 applicability=uncertain을 함께 전달한다. 호출한 에이전트는 원문·관계 근거를 읽고 의미를 해석하며 그 해석을 도구가 검증한 사실처럼 표현하지 않는다.

`ContextResult`는 `items: ContextItem[]`, `conflicts[{sources[], reason}]`, `relations: RelationView[]`(확인한 1홉 관계의 방향·범위·근거), `evidence_status: found | insufficient | none`, `limitations[]`, `truncated: bool`이다. evidence_status=found는 관련 근거를 찾았다는 뜻이며 정답 완전성·외부 사실 검증을 보장하지 않는다. ContextInput.limit는 기본/최대 10개 기록이며 구간은 위 최대 20개 예산을 공유한다. knowledge_search와 knowledge_context는 답변 모델 로그인·연결을 요구하지 않는다. 웹 답변의 의미 해석·생성에만 선택한 모델 어댑터를 사용하며 그 연결 실패가 기록 CRUD와 검색 도구를 막지 않는다.

## 답변과 스트리밍

각 요청은 독립된 request_id를 갖고 서버는 실행 중 상태만 유지한다. 질문·답변 원문을 DB·영구 체크포인트·본문 로그에 자동 저장하지 않는다. 서버 인증 토큰이나 내부 디버그 상태를 스트림에 넣지 않는다.

이벤트는 모두 request_id를 포함하고 한 요청에서 다음 순서를 따른다.

1. `started` → `progress`(searching/gathering/answering 등): 요청 수락과 진행만 표시한다.
2. 모델은 공급자 스트림으로 생성할 수 있지만 앱은 답변 구간을 내부에서 모은다. 저장 사실과 일반 설명을 나누고 해당 구간의 의미상 근거와 현재 revision·삭제·출처 상태를 검사한 뒤 `answer_part`로 전달한다. 미검사 토큰을 확정된 저장 사실처럼 바로 게시하지 않는다.
3. 이미 전달한 answer_part를 포함한 전체 SourceRef와 상태 세대를 마지막으로 재검사한다. 모두 유지되면 `completed`와 최종 AnswerResult를 보낸다.
4. 첫 answer_part 전 근거가 변경됐으면 예산 안에서 한 번 다시 조회·생성할 수 있다. 이미 전달한 근거가 수정·삭제·무효화됐으면 `invalidated`(영향받은 part ID와 사유)를 보내고 **completed를 보내지 않는다**. 화면은 해당 답변을 현재 유효한 답으로 표시하지 않고 새 검색 재시도를 제공한다.
5. 취소는 `cancelled`, 실행 실패는 `error`로 종료한다. 실패한 일부 결과를 completed로 바꾸지 않는다. 일시적 오류 재시도와 상태 변경 재시도는 전체 시간·호출 예산을 공유한다.

형식·참조 검증과 모델의 근거 해석은 다른 검사다. 근거 없는 개인 경험을 만들어 내지 않고 부족하면 insufficient/none으로 답한다. 일반 설명은 내부에서 별도 Part로 분류하고 개인 기록처럼 인용하지 않는다. 화면에서는 반복된 유형 제목 대신 문장 자체로 일반 설명임을 밝힌 하나의 글로 이어 보여준다. source 변경을 기다리면서 긴 SQLite 트랜잭션을 유지하지 않는다.

브라우저는 현재 검색 입력·응답·선택한 출처만 화면 상태로 보유한다. 새 검색을 시작하면 새 request_id를 활성화하고 이전 요청을 취소할 수 있다. 이전 요청의 늦은 이벤트는 현재 화면을 덮어쓰지 않는다. 서버에서도 취소한 요청이 새 작업을 시작하지 않게 한다. 다음 질문에 이전 답변·대화 이력을 붙이지 않는다.

웹 검색 제출은 `/questions` 요청 하나만 보낸다. 별도 `/search` 결과 목록을 병렬 로딩하지 않는다. `completed`의 검증된 문단을 하나의 답변 영역으로 표시하고 실제 인용한 SourceRef에 작은 번호를 붙인다. 같은 출처는 필드 값으로 비교해 같은 번호를 사용한다. `/search`는 명시적 API·MCP 검색을 위해 유지한다. [화면·출처·저장 초안 기준](../specs/workspace.md)

## 오른쪽 출처 패널

답변의 출처 클릭은 정확한 SourceRef를 source_get으로 다시 검증한다. SourceDetail에는 저장본 revision·span·해당 Node·주제·출처 상태를 담고 오른쪽 슬라이드 패널에서 보여준다. 이미 수정된 출처라면 요청한 과거 저장본을 표시하면서 과거 버전임을 알리고 현재 버전으로 이동할 수 있게 한다. 기존 인용을 현재 본문으로 조용히 바꾸지 않는다.

삭제된 부모의 현재/과거 본문과 Node는 반환하지 않는다. NOT_FOUND이면 패널의 이전 내용도 지우고 열 수 없는 출처임을 표시한다. 빠르게 다른 출처를 클릭했을 때 늦은 이전 응답이 패널을 덮지 않도록 request_id와 선택한 SourceRef/패널 요청 ID를 함께 검사한다.

completed는 그 시점의 검증 결과다. 이후 기록이 바뀌어도 영구적으로 유효하다는 뜻은 아니다. 같은 화면에서 관련 기록을 수정·삭제했다면 해당 표시를 무효화하고, 새 출처 클릭·새 검색에서는 항상 서버 상태를 다시 확인한다.

## 수용 사례

- Node 없는 짧은 메모와 512토큰을 넘는 본문 후반 내용이 검색되며 전체 저장본은 보존된다.
- 여러 청크가 같은 Node에 걸리거나 Node-only 주제를 가진 혼합 기록에서도 중복 점수 부풀림·다른 구간의 주제 오적용이 없다.
- “발표는 짧게, 학습은 예제와 함께”를 충돌로 합치지 않고 “학습도 이제 짧게”라는 명시적 변경은 해당 구간에만 적용한다. 옛 조건만 검색해도 들어오는 대체 관계를 확인한다.
- AI 제안·사용자 결정·실행 결과를 구분하며 문서 속 지시를 현재 실행 명령으로 취급하지 않는다.
- 출처 A1→A2 정정 후 새 B revision의 재검토가 성공하면 근거로 다시 쓰고 과거 출처는 이력에 남는다. 단순 빈 sources로 우회하지 않는다.
- 검색 뒤 스트리밍 중 삭제·수정된 근거는 completed로 확정하지 않는다. 출처 클릭 시 삭제됐으면 과거 본문도 열리지 않는다.
- 새 검색 뒤 도착한 이전 이벤트와 이전 패널 응답은 현재 화면을 덮지 않는다. 두 검색 사이에 대화 이력이 자동 전달되지 않는다.

이 문서는 동작 계약이다. 실제 Codex·OAuth·모델 호출과 제한된 한국어 합성 자료의 결과는 [검증 안내](../guides/testing.md)에 기록했다. 네이티브 OS와 더 큰 실사용 자료의 품질 검증은 별도다.
