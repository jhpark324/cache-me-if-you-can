# 유지보수성 점검과 후속 경계

- 기준: [현재 구조](current-system.md), [백엔드·웹 구성 경계](component-boundaries.md), [자동 검증](../guides/testing.md)
- 판단: **로컬 MVP의 정합성 기반은 좋지만, 책임 집중과 규모 확장 비용은 남아 있다.** 파일 수나 테스트 개수만으로 유지보수성이 충분하다고 판단하지 않는다.

## 유지할 기반

| 기반 | 유지보수 효과 |
| --- | --- |
| HTTP·MCP 공통 입력과 RecordService | 저장·삭제·충돌 의미가 클라이언트마다 달라지는 것을 줄인다. |
| immutable revision·FK·CHECK·trigger | 앱 코드가 실수해도 과거 본문 변경과 삭제 복원을 DB가 거절한다. |
| expected revision/state + request ID receipt | 동시 정정·재전송을 새 정상 작업과 구분한다. |
| SQLite 정본 + 재생성 가능한 Lance projection | 모델·검색 교체가 원본 기록을 파괴하지 않는다. |
| 저장과 outbox의 같은 트랜잭션 | 저장 성공 뒤 색인 작업을 잃는 경로를 줄인다. |
| 현재 SourceRef·세대 재검증 | 오래된 색인과 진행 중 답변이 수정·삭제를 무시하지 않게 한다. |
| 격리 SQLite/Lance·브라우저 회귀 | 사용자 데이터와 계정에 의존하지 않고 실패를 재현한다. |

## 현재 책임 경계

- `record_filters.py`: 목록·검색·그래프의 유형/주제 선택을 한 구현으로 제공한다.
- `concept_labels.py`: 저장된 표현과 검색·중복 후보 비교 키를 분리한다. 동명이의 개체를 자동 병합하지 않는다.
- `background.py`: 주기 작업의 오류 복구·취소·비밀 없는 경고를 공통화한다.
- 웹의 설정 패널·공통 표시·주제 카탈로그를 화면 조립 코드와 분리한다. 주제 페이지네이션·취소·재시도·갱신이 편집기와 홈에서 일관되게 동작한다.
- 소스 등록 후보 검사·잠금 설치·CI는 환경과 검증 조건을 재현하는 경계다.

| 우선순위 | 대상 | 근거 | 완료 기준 |

| 높음 | 출처 resolver와 읽기 snapshot 인터페이스 | `search.py`·`questions.py`가 RecordService 내부 메서드에 의존한다. 공유 출처 캐시는 개선했지만 매우 깊은 재귀 체인은 남는다. | 기존 출처·삭제·동등성 회귀 유지, 예산 초과와 실제 무효 상태 구분, 새 요청에서 반드시 재검증 |

| 중간 | API 타입 생성·계약 검사 | 서버 Pydantic과 TS 타입을 수동으로 맞춘다. | OpenAPI의 공통 타입 생성, CI 드리프트 검사, SSE의 별도 판별 union 명세 |

| 배포 전 | 네이티브 설치·단일 배포물 | 소스 설치만 검증. wheel에 프런트 미포함, Intel Mac/Windows ARM 의존성 관문이 있다. | OS/아키텍처 매트릭스 설치→CRUD→검색→OAuth→MCP→재시작 증거 |

책임 분리는 실제 중복·경합과 측정한 비용을 기준으로 진행한다. 새로운 프레임워크나 저장소 도입 전에 위 경계를 계약과 회귀 검증으로 고정한다.

```mermaid
flowchart LR
    Current[공통 도메인 + 테스트] --> Fixed[필터·비교키·워커·웹 로딩 분리]
    Fixed --> Resolver[공개 출처 resolver 계약]
    Resolver --> Query[페이지네이션·후보 비용 측정]
    Query --> Split[조회/변경/색인 책임 분리]
    Split --> Scale[실제 사용 규모 재검증]
    Fixed --> Web[검색·출처 요청 상태 분리]
    Web --> Types[API 타입/정적 분석 CI]
```

분리의 목표는 책임별 수정 범위를 줄이는 것이다. 그래프 DB, 분산 큐, 마이크로서비스, 전역 상태 라이브러리를 추가하는 것이 이 점검의 결론은 아니다.
