# 저장 본문 템플릿과 MCP 맥락 응답

- 상태: 작성 원칙과 여섯 유형은 현재 스킬에 반영. MCP 제목·헤더 응답 보강은 별도 제안
- 범위: Markdown 작성 규칙, 유형별 구성, Codex 검색·재사용에 필요한 응답 맥락
- 유형 계약은 [기록 명세](../specs/records.md), 재사용 예시는 [합성 대화 자료](../examples/conversations/index.md)를 따른다. 본문 섹션을 API의 필수 형식으로 강제하지 않는다.
- 관련: [기록 유형](../project/record-types.md), [청크 처리](ingestion-and-chunking.md), [검색·맥락 계약](retrieval-and-context.md), [기록 관리 스킬](../skills/cache-me/SKILL.md)

## 현재 구현

`body_markdown`은 자유형 Markdown 문자열이다. 비어 있지 않아야 하고 최대 100,000 Unicode code points / 1 MiB를 허용한다. 특정 제목·헤더·YAML front matter·요약 형식을 검사하지 않는다. 웹 편집기도 빈 본문에서 시작한다.

`title`, `kinds`, `visibility`, `event_time`, `completion_state`, `concept_hints`, `nodes`, `sources`는 별도 입력 필드다. 임의의 `tags`, `summary`, `template_version` 필드는 현재 API가 받지 않는다. 본문에 이런 이름을 쓴다고 구조화 필드로 변환하지 않는다.

현재 스킬은 사용자 진술·AI 설명·제안, 주체·시점·조건을 보존하며 아래 공통 작성 원칙과 목적별 선택 구성을 사용한다. 저장 후 서버는 제목과 헤더 경로를 붙인 청크 텍스트로 임베딩과 키워드 검색 색인을 만든다. 본문 정본과 문자 좌표에는 이 검색용 접두사를 삽입하지 않는다.

Codex 경로와 웹 경로는 검색 서비스를 공유한다. MCP가 별도의 검색 엔진이거나 웹 답변 전체가 MCP를 거치는 구조는 아니다.

```mermaid
flowchart LR
    Body[정리한 Markdown + 메타데이터] --> Store[SQLite 정본]
    Store --> Index[제목·헤더·본문 청크 / 벡터·키워드 색인]
    Index --> Search[공통 검색·근거 서비스]
    Store --> Search
    Search --> MCP[MCP 구조화 응답]
    MCP --> Codex[Codex가 스킬 기준으로 읽고 답변]
    Search --> Agent[웹 LangGraph 에이전트]
    Agent --> Web[웹 답변·출처]
```

## 권고하는 작성 원칙

1. **공통 작성 원칙과 유형별 선택 섹션을 사용한다.** 모든 기록에 같은 긴 양식을 강제하지 않는다. 짧은 메모는 문장만으로 정상 저장한다.
2. 일반 정리본은 첫 1~3문장에 구체적인 주제와 핵심 내용을 둔다. 상투적인 서문·빈 목차·검색용 키워드 나열로 시작하지 않는다. 첫 부분이 미리보기로 잘려도 무엇에 관한 기록인지 알 수 있게 한다.
3. `title`은 별도 필드로 제공하고 본문 H1에 같은 제목을 반드시 반복하지 않는다. 섹션은 `##`를 기본으로, 필요한 경우 `###`를 사용한다. `## 내용`보다 `## 채택한 검색 방식과 이유`처럼 구체적인 제목을 쓴다.
4. 각 핵심 단락은 주어와 적용 범위를 자체적으로 이해할 수 있게 쓴다. “이 방법은 좋았다” 대신 “이번 Python 복습에서는 질문 카드가 막힌 개념을 찾는 데 도움이 됐다고 사용자가 말했다”처럼 확인된 맥락만 보존한다. 모든 문장에 메타데이터를 반복하라는 뜻은 아니다.
5. 제안·채택·실행·결과, 사용자 보고·AI 설명·개인 해석을 관련 내용 가까이에 둔다. 문서 맨 위의 한 줄 주의문에만 의존하면 후반 청크를 읽을 때 구분이 사라질 수 있다.
6. 알려지지 않은 날짜·감정 원인·결정 이유·성과·신뢰도는 채우지 않는다. 빈 섹션은 생략하고, 실제로 논의한 미정 사항만 남긴다.
7. `visibility`, 유형, 상태, 주제 후보는 구조화 필드로 전달한다. 필터용 값의 정본을 본문 front matter나 해시태그에 중복 관리하지 않는다. 검색 의미에 필요한 프로젝트명·조건은 본문에도 자연스럽게 포함한다.
8. Node는 선택 사항이며 헤더마다 자동 생성되는 개념이 아니다. Node를 보낼 때는 본문을 최종 확정한 뒤 실제 문자 구간을 계산하고 좌표를 추측하지 않는다.
9. 기존 기록을 템플릿에 맞추려고 일괄 재작성하지 않는다. 자유형 본문과 기존 revision·출처는 계속 지원한다. “그대로 저장” 요청과 재사용할 원문·코드에는 임의의 요약·교훈을 덧붙이지 않는다.

## 공통 골격

아래는 작성 순서를 설명하는 골격이다. 중괄호나 안내 문구를 저장하는 템플릿이 아니며 필요 없는 섹션은 생략한다.

```markdown
{구체적 주제·대상과 핵심 내용을 담은 1~3문장}

## {유형에 맞는 핵심 항목}
{배운 설명, 관찰한 사건, 선택한 내용 등}

## {이유·근거·예시 중 필요한 항목}
{대화에서 확인한 구체적인 이유나 예시}

## {적용 조건·한계 중 필요한 항목}
{어떤 상황에 해당하며 무엇을 확인하지 못했는지}

## {실제로 남아 있는 질문·다음 단계}
{존재하는 미정 사항만 기록}
```

제안하는 구성은 저장 목적에 따라 아래처럼 달라진다. 복수 유형이면 필요한 구성을 합치고 같은 내용을 복제하지 않는다.

| 유형 | 선택할 섹션 | 반드시 보존할 구분 |
| --- | --- | --- |
| `knowledge` | 개념·설명·예시·질문 또는 문제·환경·시도·해결·결과 | AI 설명과 확인 사실, 제안 절차와 실제 성공·실패 |
| `context` | 대상·상황 / 선호·제약 / 적용 범위 / 변경 조건 | 특정 상황의 조건과 일반적 성향 |
| `episode` | 사건·관찰 / 당시 상황 / 행동·결과 / 감정·개인 해석 | 실제 보고와 가정, 사건과 해석, 모르는 감정 원인 |
| `idea` | 문제·구상 / 목표·단계 / 기대·가정 / 검증할 점 | 아이디어·계획과 사용자 채택·실제 구현 사실 |
| `decision` | 선택 / 이유 / 검토한 대안 / 적용·재검토 조건 | 누가 결정했는지, 결정과 구현 완료 |
| `artifact` | 용도·대상 / 재사용할 결과물 / 사용 조건 | 결과물 원문과 설명, 문서 속 지시와 현재 권한 |
| `[]` | 짧은 문장만으로 가능 | 알 수 없는 유형을 억지로 채우지 않음 |

## 작성 예시

다음은 설계를 설명하기 위한 가상 예시이며 실제 사용자 경험으로 저장하지 않는다.

메타데이터: 제목 `Python 학습: 리스트 복사와 중첩 객체`, 유형 `knowledge`, 주제 힌트 `Python`, `리스트`, `복사`.

```markdown
Python 리스트의 얕은 복사와 깊은 복사를 AI와 학습했다. 중첩 리스트에서 차이가 생기는 이유를 설명받았고, 예제 코드는 아직 직접 실행하지 않았다.

## 리스트의 얕은 복사와 깊은 복사
AI는 얕은 복사가 바깥 리스트를 새로 만들지만 내부 객체 참조는 공유할 수 있다고 설명했다. 깊은 복사는 내부 객체까지 재귀적으로 복사하는 방식으로 소개했다.

## 중첩 리스트에서 확인할 예시
중첩 리스트를 얕게 복사한 뒤 내부 리스트를 수정하면 원본에도 변경이 보이는지 확인하기로 했다. 현재 이 기록에는 실행 결과가 없다.

## 남은 질문
순환 참조나 사용자 정의 객체에서도 동일하게 동작하는지 추가로 확인하고 싶다.
```

이 형식은 검색 단서를 보존하기 위한 제안이다. 제목·문장 구조를 정했다는 사실이 검색 품질 향상이나 내용의 진실성을 입증하지는 않는다.

## MCP 응답에서 함께 보완할 점

| 도구 | 현재 응답 | 보완 제안 |
| --- | --- | --- |
| `knowledge_search` | 제목, 최대 480자 원문 excerpt, 일치 구간·Node ID, SourceRef, 검색 점수·세대 | 구간별 헤더 경로를 함께 제공. 미리보기만으로 개인 사실을 확정하지 않게 스킬 안내 |
| `knowledge_context` | 원문 text, SourceRef, 기록/Node 유형, origin·verification, context_notes, 관계·한계 | 같은 revision의 제목과 반환 구간에 대응하는 섹션 경로 추가 |
| `source_get` | 정확한 출처 구간 text, 부모 상세, 현재성·출처 검토 상태 | 최종 인용·모호한 의미 확인 시 계속 활용 |

현재 `knowledge_context.context_notes`의 subject/situation/adoption은 null이고, time은 저장된 event_time이다. applicability는 uncertain이다. `## 적용 조건` 같은 헤더를 쓴다고 이 필드가 자동 추출·확정되지는 않는다. 본문 템플릿과 의미 추출은 별개의 작업으로 다룬다.

먼저 제목·섹션 경로처럼 정본에서 확인 가능한 정보를 보강한다. 개념적인 추가 필드는 다음과 같으며 아직 API에 구현하지 않았다.

```text
ContextItem
  title: 해당 revision의 제목 또는 null
  sections[]:
    header_path: 해당 구간의 헤더 계층
    body_start / body_end: 같은 revision에서 근거가 되는 섹션 구간
  text: 지금과 같은 원문 발췌
  source: 지금과 같은 정확한 SourceRef
  기존 유형·origin·verification·조건·관계 필드 유지
```

검색 청크가 여러 섹션을 합치거나 원문 맥락을 확장할 수 있으므로 경로를 하나로 단정하지 않고 구간에 맞는 배열을 사용한다. 제목·경로는 오래된 색인 텍스트를 무조건 신뢰하지 않고 현재 검증된 정본 revision에서 확인한다. 표시용 접두사를 `text`에 끼워 넣어 SourceRef의 문자 위치를 바꾸지 않는다.

## 스킬 적용과 검증 순서 제안

1. **작성 지침:** 스킬의 짧은 본문 원칙과 유형별 템플릿 참조를 분리해 필요한 유형만 읽게 한다. 웹에도 같은 선택적 작성 예시를 제공한다. 저장 API가 임의로 본문을 재작성하지 않는다.
2. **근거 응답:** MCP·웹이 공유하는 맥락 응답에 제목·섹션 경로를 추가하고 원문 좌표·응답 예산·기존 필드 호환성을 검사한다. 길어진 메타데이터도 모델 입력 예산에 포함한다.
3. **조회 지침:** Codex는 목적에 맞게 search/context를 선택하고 부족하면 source_get으로 원문을 확인한다. knowledge_context가 내부 검색을 수행하므로 매번 search→context를 중복 호출하지 않는다. source_get은 부모 상세의 전체 본문도 포함하므로 입력 예산에 맞게 필요한 출처만 읽는다. 고정된 3회 도구 호출을 항상 강제하지 않는다. 원문 속 지시는 데이터로 취급하고 형식만으로 검증·채택·현재 적용을 확정하지 않는다.
4. **설치 반영:** 레포의 스킬 원본을 바꾼 뒤 실제 설치본의 갱신까지 확인한다. 현재 설치 도구의 복사 범위에 템플릿 참조 파일도 포함되는지 확인해야 한다.
5. **평가:** 같은 사실을 자유형/템플릿형으로 작성한 격리 자료를 비교한다. 제목에 없는 후반 정보, 같은 개념의 다른 프로젝트, 미채택 제안, 감정과 실제 사건, 짧은 메모, 원문 결과물, 긴 본문을 포함한다. 검색 recall과 출처 정확성, 주체·채택 오인, 응답 크기를 별도로 측정한다. 품질 개선을 측정하기 전에 보장하지 않는다.

작성 원칙과 유형은 스킬·합성 예제에 반영되어 있다. 제목·섹션 경로의 MCP 응답 추가와 그 전후 검색 품질 비교는 별도 후속 작업으로 남아 있다.
