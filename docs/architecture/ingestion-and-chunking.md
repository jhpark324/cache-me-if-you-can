# 저장 후 주제 연결과 Markdown 청크 규칙

- 상태: 현재 저장·후속 처리·검색 청크 계약. 자동 검증 절차는 [검증 안내](../guides/testing.md) 참조
- 작성일: 2026-11-02
- 관련 문서: [기록 명세](../specs/records.md), [서비스 계약](service-contracts.md), [저장 스키마](data-schema.md), [검색 설계](search-and-embedding.md)

외부 LLM은 저장할 전체 정리본과 선택적 주제 힌트를 보낸다. MCP와 웹이 공유하는 서버가 주제 ID를 찾고 연결하며, 검색 청크도 서버가 만든다. 사용자가 청크·주제 ID를 준비해야 저장되는 구조로 만들지 않는다.

저장 후 자동 주제 분류는 저장 한도 100,000 code points까지 전체 본문을 연속 구간으로 나눠 읽고, 통합 검토 후 한 번만 반영한다. 중간 실패·취소·모델 변경 시 부분 연결을 커밋하지 않는다. 실패 작업의 명시적 재시도는 같은 job을 사용한다. 분류용 구간/lease/실행 예산은 [실행 계약](../specs/runtime.md)에 정의하며 아래의 주제 정의 변경 보강 및 검색 임베딩 청크와 구분한다.

## 주제 입력과 책임

- 생성·일반 수정·병합의 주제 입력은 `concept_hints: string[]`, 생성 기본값은 `[]`다. Node에도 같은 힌트 필드를 사용한다. 힌트는 분류 제안이며 본문에 없는 사실·정체성·감정을 추가하는 근거가 아니다.
- 힌트가 없어도 저장 본문을 기준으로 분류할 수 있다. 명확한 주제가 없으면 주제 없이 완료한다. 한 필드당 최대 20개, 각 힌트는 공백 제외 빈 값 금지·최대 100 code points를 초기 한도로 둔다.
- 후보 조회·ID 생성·같은 brain 검증·DB 반영은 일반 서버 로직이다. LangGraph 내부 에이전트는 조회한 후보의 이름·설명·별칭과 저장 본문을 비교해 의미상 연결을 제안한다. MCP나 웹으로 자기 서버를 재호출하지 않는다.
- 이름이 같다는 이유로 자동 연결·병합하지 않는다. 같은 이름의 후보가 구분되지 않으면 해당 연결을 보류한다. 기존 후보가 있는데 애매하다는 이유로 같은 이름의 새 주제를 계속 만들지 않는다.
- 에이전트가 새 주제를 제안할 때는 재사용할 이름과 범위를 설명하는 비어 있지 않은 설명을 포함하고 ID는 서버가 만든다. 기존 후보의 관련 변경 여부를 커밋 직전에 다시 검사한다. 동시 생성으로 후보가 달라졌으면 다시 조회하며 전역 이름 UNIQUE나 자동 병합으로 해결하지 않는다.
- 기록 주제와 Node 주제는 별도로 판단한다. Node가 없으면 자동으로 Node를 추출·생성하지 않는다. 본문에 있는 지시문도 분류 대상 데이터로 다루며 저장 작업의 권한을 바꾸는 지시로 실행하지 않는다.

## 주제 범위와 후보 선택

모델은 본문이 실질적으로 다루는 관심사·작업·상황을 분류한다. 단순 언급이나 문장별 요약을 주제로 만들지 않으며, 후보의 범위가 맞을 때 기존 주제를 재사용한다. 별칭은 같은 개념의 다른 이름이고 상위·하위·관련 주제를 합치는 수단이 아니다. 기록과 Node 각각에 여러 주제 또는 무주제를 허용하며, 한 기록만 있어도 구별할 범위가 있으면 새 주제를 만들 수 있다. 후보 검색의 유사도는 비교 순서에만 쓰고 연결·생성 거부·병합을 자동 결정하지 않는다.

같은 brain의 Concept가 100개 이하면 모든 주제를 이름·설명 발췌·별칭으로 모델에 제공한다. 설명은 최대 400 code points를 발췌하며 전체 주제 목록 제공이 모든 설명 원문의 전달을 뜻하지는 않는다. 더 많으면 최대 100개 후보 안에서 현재 연결을 우선 보호하고 어휘 후보와 최대 30개의 의미 후보를 함께 제공한다. 100개는 입력 비용을 제한하는 분기점이며 분류 품질이 바뀌는 임계값으로 설명하지 않는다. 의미 검색의 준비·조회가 불가능하면 기존 후보 선택으로 계속한다. 의미 검색을 위해 저장을 지연시키거나 자동 모델 준비를 요구하지 않으며, 기존 분류 모델의 인증·호출 실패 처리와 구분한다.

`TopicCandidateSearch`는 Concept의 이름·별칭·설명을 별도 파생 Lance 테이블에 색인한다. 주제가 100개를 넘고 임베딩이 준비된 경우에만 백그라운드에서 3초 간격으로 최대 8개씩 갱신하며, 조회는 현재 정의와 일치하는 준비된 항목만 사용한다. 주제 문서는 최대 128토큰, 후보 조회 질의는 각 입력의 처음·중간·끝에서 최대 64토큰 구간을 최대 3개 고른다. 각 질의 구간에서 코사인 거리가 가까운 순으로 주제 후보를 고르고, 1위부터 `1 / (60 + 순위)`를 더해 최대 30개를 남긴다. 예를 들어 앞부분에서 2위, 끝부분에서 1위인 주제는 `1/62 + 1/61`을 얻어 모델에 보여줄 후보가 된다. 최종 연결은 분류 단계에서 판단한다. 캐시가 비었거나 조회에 실패하면 어휘 후보 경로를 유지한다.

최종 분류 통합 뒤 새 주제 제안이 있으면 그 정의로 처음 모델에 보여주지 않았던 기존 후보를 찾는다. 새 비교 후보가 발견될 때만 작업당 최대 한 번 제안 정의를 검토하며, 같은 개념의 기존 주제 재사용·제안 유지·보류를 선택한다. 원래 본문과 기존 연결을 다시 분류하지 않고 모든 작업에 두 번째 호출을 추가하지 않는다. 의미 후보 확인에 실패해도 이를 분류 실패로 바꾸지 않으며, 의미 유사도만으로 신규 제안을 기존 주제에 치환하지 않는다. 자동 병합은 수행하지 않으며 주제 세분화의 적절성이나 중복 방지를 보장하지 않는다. 범위 설명 필수는 내부 모델의 새 주제 제안에 적용하고, 수동 `CreateConceptInput`의 선택적 설명 계약은 유지한다.

후보 선택과 추가 검토는 현재 연결·명시적 정정·버전 검증을 대체하지 않는다. 최종 커밋은 아래 후속 작업 계약을 따르며 본문이나 사용자가 정정한 연결을 오래된 자동 판단으로 덮어쓰지 않는다.

### 후보 순위와 이름 충돌 비교

후보 선별과 주제 등록은 서로 다른 문자열 비교를 쓴다.

| 비교 시점 | 입력과 규칙 | 영향 |
| --- | --- | --- |
| 분류할 구간의 어휘 후보 선별 | 구간 본문, 기록 힌트, 구간과 겹치는 Node의 힌트를 모아 대소문자를 접는다. 주제 이름과 각 별칭이 문자열에 포함됐는지 각각 한 번씩 센다. 횟수가 같으면 최근 수정 시각, ID 내림차순으로 순서를 정한다. | 예컨대 ‘전송 계층’의 별칭이 `transport layer`면 힌트 `Transport Layer`도 후보 순서에 기여한다. 같은 표현을 본문에 반복해도 그 표현이 주는 점수는 하나다. 실제 연결은 모델이 본문과 주제 범위를 비교한 뒤에 결정한다. |
| 새 주제의 커밋 직전 | 같은 서재에 있는 주제 이름·별칭과 제안된 이름·별칭을 NFC로 정규화하고 대소문자를 접고 연속 공백을 하나로 줄여 비교한다. | 이미 `Transport Layer`가 있으면 `transport  layer`라는 이름의 신규 제안은 충돌한다. 서버는 두 ID를 자동 병합하지 않고 재시도 때 후보를 다시 읽는다. |

## 저장과 후속 작업

1. 입력과 출처를 검증하고 본문·첫 revision·receipt·색인 작업·주제 연결 작업을 같은 SQLite 트랜잭션에 저장한다. 본문 변경이나 주제 힌트/Node 변경에도 해당 새 revision의 작업을 만든다.
2. 실제 저장본과 `concept_state.status=pending`을 반환한다. 저장 응답을 기다리게 하는 필수 LLM 호출을 두지 않는다. 주제 연결 완료 전에도 본문 색인을 진행하고 주제 조건 없는 검색을 제공한다.
3. 작업자는 로그인·모델 선택·호출 가능 상태를 확인한 뒤 작업을 가져간다. 모델이 아직 준비되지 않은 새 작업은 `pending`으로 기다린다. 작업을 가져간 뒤 호출이 실패하면 `failed`와 오류 분류를 기록한다. 어느 경우든 본문은 남으며 모델 호출 중에는 DB 쓰기 트랜잭션을 열지 않는다.
4. 커밋 직전에 기록과 주제를 각각 검사한다. 기록이 삭제되거나 요청한 기록 버전·상태 버전이 지나갔으면 옛 작업은 `superseded`가 된다. 일반 수정에 분류가 필요하면 최신 버전의 작업을 등록하고, 명시적 주제 정정은 여기서 마친다. 반면 연결할 기존 주제의 상태 버전이 바뀌었거나 새로 제안한 이름·별칭이 기존 이름·별칭과 겹치면 `VERSION_CONFLICT`로 해당 시도를 중단한다. 같은 작업이 재시도될 때 후보 목록을 새로 읽는다.
5. 연결이 바뀌면 새 revision을 `change_kind=concept_enrichment`, `created_via=system`으로 생성한다. 본문·제목·유형·완료·사건 시각·Node 의미/span·공개 범위·출처를 유지하고 주제 연결만 바꾼다. Node는 기존 불변 revision 규칙에 따라 새 ID로 복제한다. 안전한 메타데이터 승계 규칙을 적용한다.
6. 새 revision·상태 버전·검색 세대·색인 작업·주제 작업 결과를 원자적으로 반영한다. 주제만 반영한 revision은 또 다른 자동 분류를 시작하지 않는다. 연결이 바뀌지 않았으면 revision을 만들지 않고 작업만 완료한다.

작업의 고유성은 `(capture_id, requested_revision_id, expected_state_version, policy_version)`이며 요청 재시도는 기존 작업을 재사용한다. 새 작업의 정책 버전은 `concept-v2`이며 기존 작업을 일괄 교체하거나 저장된 기록을 일괄 재분류하지 않는다. `applied_revision_id`와 완료 상태를 커밋과 함께 남겨 응답 유실 뒤에도 주제·revision을 중복 생성하지 않는다. 실패한 실행은 같은 job의 lease·attempt를 갱신해 재시도한다. 유한한 실행 시간·재시도 횟수는 구현 설정으로 제한하고 모델 미연결 상태에서 무한 반복하지 않는다.

`concept_state`는 본문 저장·색인 준비와 별개인 `pending | running | ready | failed` 상태다. `ready`에는 주제가 없거나 일부 후보를 연결하지 않은 정상 완료도 포함한다. 모호한 후보는 내부 작업의 미해결 힌트에 보존하고 확인한 연결만 반영한 뒤 `completed`로 마친다. 공개 응답의 `unresolved_hints` 필드는 호환성을 위해 빈 배열로 유지하며 사용자 검토를 요구하지 않는다. 이전 `needs_review` 작업은 데이터 변경 없이 `ready`로 조회하고, `superseded` 작업은 최신 작업의 상태를 가리지 않도록 조회 대상에서 제외한다. 늦은 실패·완료가 최신 revision의 상태를 덮어쓰지 않도록 작업의 요청/반영 revision과 연결한다. 과거 저장본을 조회할 때 현재 작업 상태를 과거 결과인 것처럼 표시하지 않는다.

`concept_hints` 생략은 수정 시 기존 힌트를 유지하고, `[]`는 힌트를 비운다. 빈 힌트만으로 기존 연결을 모두 없앴다고 해석하지 않는다. 새 본문/힌트로 분류를 다시 할 때는 현재 연결도 후보로 평가한다. 순수 공개 범위·완료·유형 변경 때문에 새 의미 판단을 반복하지 않으며 미완료 작업이 버전 충돌한 경우에만 최신 대상으로 이어간다.

명시적 정정은 `capture_set_concepts(request_id, capture_id, ExpectedVersion, concept_ids, node_concepts?)`로 처리한다. `concept_ids`는 기록 주제의 전체 목록이며 `[]`는 비우기다. `node_concepts`는 생략하면 기존 Node 연결 유지, 제출하면 현재 Node별 `{node_id, concept_ids[]}` 전체 목록으로 교체하며 빠진 Node는 빈 연결로 처리한다. Node 소속·ID·조회 자격을 검증한다. 이 API·MCP 경로는 명시적 정정의 호환성 계약으로 유지하며 기본 저장의 선행 호출이 아니다. 웹은 자동 분류 결과만 표시하고 수동 정정 진입점을 제공하지 않는다. 결과는 새 `edit` revision으로 남기고 옛 자동 작업을 무효화하며 이 정정 자체로 재분류를 시작하지 않는다. 이후 사용자가 본문·힌트·Node를 바꾸면 그 새 저장 요청의 범위에서 다시 분류한다.

`concept_ids`는 읽기 결과·검색 필터·위 명시적 정정 계약에 유지한다. 생성·일반 수정·병합의 기본 입력에는 넣지 않는다. 내부 주제 판단 실패를 외부 LLM의 ID 탐색 의무로 되돌리지 않는다.

## 주제 정의 변경과 기존 기록 연결 보강

새 Concept 생성이나 이름·설명·별칭의 실제 변경과 같은 트랜잭션에서 보강 작업을 등록한다. 같은 정의는 중복 등록하지 않고 연속 변경은 현재 정의를 기준으로 모아 처리한다. 설치·업데이트 시 기존 주제를 순회해 작업을 만들지 않는다. 저장 후 분류가 새 주제를 만들 때에도 이 규칙을 적용하며, 주제 연결만 추가한 기록 revision은 새 분류·보강을 재귀적으로 시작하지 않는다.

작업자는 주제 정의의 이름·설명·별칭에서 각각 최대 64토큰 질의를 만들어 기존 본문 벡터·FTS 검색을 실행하고 최대 20개 고유 기록을 고른다. 이미 연결된 주제에서 후보를 얻는 검색 경로는 사용하지 않는다. 기록당 최대 4,000 code points의 본문을 최대 5개 기록씩 모델에 제공하며, 긴 본문은 앞 1,000자와 검색 지점 주변 3,000자를 발췌한다. 재시도를 포함한 작업 전체의 모델 호출은 최대 4회다. 발췌가 주제 범위를 판단하기에 부족하면 보류하고, 전체 본문을 검토한 결과로 설명하지 않는다. 후보·호출 상한이 저장소 전체의 검색 비용을 제한하는 것은 아니다. 현재 정확 벡터 검색은 유효한 색인 벡터를 조회하며, 연결 변경 후에는 기존 규칙에 따라 재색인 작업도 발생한다.

일반 저장 후 분류 한 건, 보강 한 건을 순서대로 처리한다. 검색·색인이 준비되지 않으면 claim 전에 대기하고, 일부 색인이 미완료이거나 일반 분류가 `pending/running`이면 가능한 기록을 처리한 뒤 지연한다. 정책은 `topic-backfill-v1`, claim은 최대 3회, 재시도 간격은 30초, 모델 호출 제한은 90초, lease는 120초다. 불확실한 판단·일부 처리·예산 소진은 내부 `partial`로 구분하며 정상적인 0건 완료로 기록하지 않는다. 저장 후 분류의 `concept_state`와 별개인 내부 작업 상태로 관리하며 새 진행·제안 화면은 제공하지 않는다.

판단은 주제 정의 해시·기록 내용 해시·정책 버전으로 재사용하되, 적용 직전 현재 주제 정의·기록 버전, 삭제·출처 유효성, 수동 정정 receipt를 다시 검사한다. 후보 준비와 적용 양쪽에서 현재 revision의 `concept_state`가 `ready`인지 확인하고 `capture_set_concepts` 이력이 있는 기록은 제외한다. `pending/running`은 완료를 기다리며 `failed`는 제외해 실제 실패의 재시도 경로를 보존한다. 일부 후보 보류 및 이전 `needs_review`는 정상 완료로 조회되므로 다른 자격 조건을 충족하면 자동 보강할 수 있다. 확정한 기록 수준의 연결만 새 `concept_enrichment` revision에 추가하고 기존 기록·Node 연결과 의미 필드를 보존한다. 같은 연결이 이미 있으면 revision과 색인 작업을 추가하지 않는다. `attach/reject` 판단만 캐시에 남기며 불확실한 보류는 확정 판단으로 재사용하지 않는다. 검색과 모델 호출 동안 쓰기 트랜잭션을 열어 두지 않으며, 판단 캐시가 현재 자격과 버전 검증을 대신하지 않는다.

## 청크의 기준과 예산

규칙 버전은 `markdown-v1`이다. **Markdown 구조 → 문단/블록 → 문장 → 토큰** 순서로 분할한다. 분할은 결정적인 서버 로직으로 수행하며 별도 LLM 호출이나 본문 재작성을 사용하지 않는다.

| 항목 | 초기 규칙 |
| --- | --- |
| 최대 입력 | 실제 `encode_document` 경로의 제목·헤더 맥락·구분자·모델 마커·특수 토큰을 모두 포함해 512토큰 이하 |
| 짧은 기록 | 전체 입력이 예산 안이면 헤더 수와 관계없이 청크 하나 |
| 구조 경계 | 최상위 블록의 ATX `#`~`######`와 Setext 헤더. 헤더 레벨·본문 위치로 경로를 유지 |
| 작은 구간 | 원문만의 토큰 수가 각각 128 미만인 인접 형제 구간은 같은 부모 아래에서 합산 전체 입력이 512 이하면 순서대로 묶음. 최상위 형제도 같은 문서 루트 아래로 취급 |
| 큰 구간 | 블록을 원문 순서로 최대한 묶고, 예산을 넘는 단일 블록만 아래 규칙으로 분할 |
| 겹침 | 단일 문단·블록을 강제 분할할 때만 같은 구간 안에서 최대 64토큰. 독립 헤더·완결 블록 경계는 기본 0 |
| 보조 맥락 | 제목과 헤더 경로를 반복할 때 구분자 포함 최대 64토큰. 전체 입력 512 안에 포함 |

512는 모델 한계나 최적값으로 입증된 수치가 아니라 현재 개발 시작값이다. 1,024와 같은 자료에서 품질·CPU 지연·총 벡터 수·겹침을 비교할 수 있도록 프로필 값으로 관리한다. 모델의 공식 문서 한도는 8,192토큰이다. [KURE-v2 모델 카드](https://huggingface.co/nlpai-lab/KURE-v2)

## 헤더·블록 처리

1. 원문 위치를 보존하는 Markdown 파서로 구조를 읽는다. 단순히 줄 첫 글자 `#`로 분리하지 않는다. 코드 펜스·들여쓴 코드·인용·목록 안의 헤더는 문서 전체의 새 섹션으로 취급하지 않는다. 헤더와 코드의 문법 판정은 [CommonMark](https://spec.commonmark.org/0.31.2/#atx-headings), 표는 [GFM 표 확장](https://github.github.com/gfm/#tables-extension-)을 따른다.
2. 긴 기록에서는 다음 문서 헤더 직전까지를 기본 구간으로 둔다. 헤더 이전 서문도 구간이며, 헤더 레벨이 뛰어도 없는 부모 제목을 만들어 넣지 않는다. 헤더만 있고 본문이 없는 상위 구간은 이어지는 하위 구간과 붙여 고립된 제목 청크를 줄인다.
3. 각 구간에서 완결된 문단·목록·인용·코드·표를 순서대로 묶는다. 예산 안에 들어오는 블록은 쪼개지 않는다. 작은 형제 구간을 묶어도 각각의 헤더 경로·범위를 메타데이터로 남기고 다른 기록끼리는 절대 합치지 않는다.
4. 단일 문단이 예산을 넘으면 문장 끝을 우선한다. 그래도 긴 문장·URL·식별자는 토크나이저 offset을 원문 code point 위치로 변환해 안전한 문자 경계에서 분할한다. decode한 토큰 문자열로 정본을 다시 구성하지 않는다.
5. 긴 목록은 항목, 표는 행, 코드는 줄 경계를 우선한다. 항목·행·코드 한 줄도 너무 길면 마지막 수단으로 토큰/문자 경계 분할을 적용하고 `split_reason`에 표시한다. 표 헤더·코드 언어 등 반복 설명은 보조 맥락 예산을 공유한다. 반복 코드 펜스를 렌더링용으로 덧붙이면 보조 맥락으로만 취급하며 원문 span을 바꾸지 않는다.
6. 강제 분할 뒤에는 직전 구간 끝의 완결 문장/줄을 최대 64토큰까지 겹친다. 완결 단위가 너무 길면 안전한 문자 경계의 suffix를 쓴다. 전체 512 예산과 새 본문의 전진을 우선해 겹침을 줄이거나 0으로 만들 수 있다. 같은 범위만 반복하는 청크는 금지한다.
7. 실제 임베딩 입력을 다시 토큰화해 상한을 확인한다. 마커·특수 토큰을 이중으로 붙이지 않는다. 초과분은 다음 청크로 이동하며 모델의 자동 truncation에 맡기지 않는다.

제목·헤더 경로는 의미를 보조하며 자동 Concept나 Node를 생성하는 근거가 아니다. 보조 맥락이 64토큰을 넘으면 현재 헤더와 가까운 조상, 제목 순서로 예산을 배정하고 안전한 문자 경계에서 줄인다. 사용한 형태와 `context_truncated`를 남기며 전체 제목·헤더 경로는 메타데이터에서 유지한다. 본문 안의 원래 헤더는 일반 본문과 함께 빠짐없이 청크에 포함한다. 보조 맥락의 축약을 원문 누락으로 연결하지 않는다.

전체 기록 한 청크의 보조 맥락은 기록 제목만 사용한다. 작은 형제 구간을 묶은 청크는 공통 부모 경로와 제목을 사용하고 각 형제의 헤더는 원문에 남긴다. 그 밖의 청크는 현재 구간의 헤더 경로와 제목을 사용한다. 코드 언어·표 헤더 보조가 필요하면 같은 64토큰 예산에서 가까운 블록 맥락을 우선한다.

문장 경계 판정기·Markdown 파서·GFM 확장 설정·토크나이저 revision은 프로필에 고정한다. `markdown-v1`의 문장 경계는 문단 안의 종결 부호(`.`, `?`, `!`, `。`, `？`, `！`) 뒤 공백/구간 끝을 후보로 삼고 소수·URL·코드 span 내부는 후보에서 제외하는 규칙으로 시작한다. 문장 판정의 품질이 낮아도 원문 범위 누락·순서 변경은 허용하지 않는다.

## 원문 참조와 예시

각 청크는 한 revision의 연속적인 원문 범위 `[body_start, body_end)`를 가진다. 원본 청크 본문은 정확히 `body_markdown[start:end]`이며 공백·개행·Unicode를 재정규화하지 않는다. 파서가 내부적으로 개행을 정규화하더라도 원문 위치로 변환하는 매핑을 유지한다. 선행·후행·블록 사이 공백도 인접 청크에 포함해 본문 전체를 덮는다.

`section_refs[]`는 해당 청크와 만나는 섹션의 원문 범위·헤더 경로를 저장한다. `context_prefix`는 실제 임베딩에 사용한 보조 맥락, `context_truncated`는 축약 여부, `split_reason`은 `whole_record | section | packed_sections | block | sentence | token`이다. 제목/헤더를 여러 청크에 반복해도 실제 근거와 Node 매핑은 `body_start/end`로 계산하며 반복한 prefix에서 가짜 인용 위치를 만들지 않는다.

예를 들어 긴 학습 기록이 `# 트랜잭션 → ## 원자성 → ## 격리성`으로 구성되면 원자성과 격리성을 우선 별도 구간으로 다룬다. 격리성만 길면 그 구간을 문단·문장 순서로 나누고 각 청크에 `트랜잭션 > 격리성` 경로를 보조한다. 짧은 메모는 같은 헤더 구조가 있어도 한 청크에 보존한다. 검색 후에는 [맥락 계약](retrieval-and-context.md)에 따라 원본 Node·섹션·앞뒤 본문을 추가 조회할 수 있으며 청크 하나만으로 답변 맥락을 제한하지 않는다.

## 구현 시 검증할 조건

- 외부 ID 조회 없는 저장, 힌트 없음, 동일 이름의 다른 주제, 잘못된 힌트, Node만의 주제, 모델 미연결·실패에도 본문 보존.
- 자동 연결과 사용자 수정·삭제·주제 정정의 경합, 동일 job 재실행, 같은 주제 동시 생성, 이전 revision 불변, 자동 연결의 재귀 방지.
- 헤더 없는 본문, 중첩·Setext·동일 제목, 코드 안의 `#`, 인용/목록 안의 헤더, 긴 코드·표·URL, CRLF·이모지·결합문자.
- 같은 프로필/원문에서 결정적인 청크, 전체 원문 범위의 합집합 보장, 512토큰 상한, 겹침 상한·전진 보장, 작은 구간 묶기와 보조 맥락/인용 분리.
- 512와 1,024 비교 시 동일 문서·질문으로 정확도·맥락 누락·p95·총 청크/벡터 수·디스크를 함께 측정. 수치를 변경하기 전 동일 조건의 실행 평가가 필요하다.
