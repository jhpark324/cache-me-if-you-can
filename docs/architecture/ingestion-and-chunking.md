# 저장 후 주제 연결과 Markdown 청크 규칙

- 상태: 현재 저장·후속 처리·검색 청크 계약. 자동 검증 절차는 [검증 안내](../guides/testing.md) 참조
- 작성일: 2026-11-02
- 관련 문서: [기록 명세](../specs/records.md), [서비스 계약](service-contracts.md), [저장 스키마](data-schema.md), [검색 설계](search-and-embedding.md)

외부 LLM은 저장할 전체 정리본과 선택적 주제 힌트를 보낸다. MCP와 웹이 공유하는 서버가 주제 ID를 찾고 연결하며, 검색 청크도 서버가 만든다. 사용자가 청크·주제 ID를 준비해야 저장되는 구조로 만들지 않는다.

현재 자동 주제 분류는 저장 한도 100,000 code points까지 전체 본문을 연속 구간으로 나눠 읽고, 통합 검토 후 한 번만 반영한다. 중간 실패·취소·모델 변경 시 부분 연결을 커밋하지 않는다. 실패 작업의 명시적 재시도는 같은 job을 사용한다. 분류용 구간/lease/실행 예산은 [실행 계약](../specs/runtime.md)에 정의하며 아래 검색 임베딩 청크와 구분한다.

## 주제 입력과 책임

- 생성·일반 수정·병합의 주제 입력은 `concept_hints: string[]`, 생성 기본값은 `[]`다. Node에도 같은 힌트 필드를 사용한다. 힌트는 분류 제안이며 본문에 없는 사실·정체성·감정을 추가하는 근거가 아니다.
- 힌트가 없어도 저장 본문을 기준으로 분류할 수 있다. 명확한 주제가 없으면 주제 없이 완료한다. 한 필드당 최대 20개, 각 힌트는 공백 제외 빈 값 금지·최대 100 code points를 초기 한도로 둔다.
- 후보 조회·ID 생성·같은 brain 검증·DB 반영은 일반 서버 로직이다. LangGraph 내부 에이전트는 조회한 후보의 이름·설명·별칭과 저장 본문을 비교해 의미상 연결을 제안한다. MCP나 웹으로 자기 서버를 재호출하지 않는다.
- 이름이 같다는 이유로 자동 연결·병합하지 않는다. 같은 이름의 후보가 구분되지 않으면 해당 연결을 보류한다. 기존 후보가 있는데 애매하다는 이유로 같은 이름의 새 주제를 계속 만들지 않는다.
- 에이전트가 새 주제를 제안해도 ID는 서버가 만든다. 기존 후보의 관련 변경 여부를 커밋 직전에 다시 검사한다. 동시 생성으로 후보가 달라졌으면 다시 조회하며 전역 이름 UNIQUE나 자동 병합으로 해결하지 않는다.
- 기록 주제와 Node 주제는 별도로 판단한다. Node가 없으면 자동으로 Node를 추출·생성하지 않는다. 본문에 있는 지시문도 분류 대상 데이터로 다루며 저장 작업의 권한을 바꾸는 지시로 실행하지 않는다.

## 저장과 후속 작업

1. 입력과 출처를 검증하고 본문·첫 revision·receipt·색인 작업·주제 연결 작업을 같은 SQLite 트랜잭션에 저장한다. 본문 변경이나 주제 힌트/Node 변경에도 해당 새 revision의 작업을 만든다.
2. 실제 저장본과 `concept_state.status=pending`을 반환한다. 저장 응답을 기다리게 하는 필수 LLM 호출을 두지 않는다. 주제 연결 완료 전에도 본문 색인을 진행하고 주제 조건 없는 검색을 제공한다.
3. 작업자는 최신 저장본과 후보를 읽고 에이전트를 실행한다. 모델 호출 동안 DB 쓰기 트랜잭션을 열지 않는다. 모델 인증 미준비·호출 실패는 이 작업의 `failed`이며 원래 저장을 롤백하지 않는다.
4. 결정 결과를 반영할 때 요청한 revision·state_version·현재 삭제 여부·후보의 상태 버전을 다시 확인한다. 달라졌으면 `superseded`로 종료한다. 삭제되지 않은 최신 기록의 분류가 여전히 필요하면 최신 버전을 대상으로 한 작업 하나만 대체 등록하며, 명시적 주제 정정 결과에는 자동 대체 작업을 만들지 않는다.
5. 연결이 바뀌면 새 revision을 `change_kind=concept_enrichment`, `created_via=system`으로 생성한다. 본문·제목·유형·완료·사건 시각·Node 의미/span·공개 범위·출처를 유지하고 주제 연결만 바꾼다. Node는 기존 불변 revision 규칙에 따라 새 ID로 복제한다. 안전한 메타데이터 승계 규칙을 적용한다.
6. 새 revision·상태 버전·검색 세대·색인 작업·주제 작업 결과를 원자적으로 반영한다. 주제만 반영한 revision은 또 다른 자동 분류를 시작하지 않는다. 연결이 바뀌지 않았으면 revision을 만들지 않고 작업만 완료한다.

작업의 고유성은 `(capture_id, requested_revision_id, expected_state_version, policy_version)`이며 요청 재시도는 기존 작업을 재사용한다. 초기 정책 버전은 `concept-v1`이다. `applied_revision_id`와 완료 상태를 커밋과 함께 남겨 응답 유실 뒤에도 주제·revision을 중복 생성하지 않는다. 실패한 실행은 같은 job의 lease·attempt를 갱신해 재시도한다. 유한한 실행 시간·재시도 횟수는 구현 설정으로 제한하고 모델 미연결 상태에서 무한 반복하지 않는다.

`concept_state`는 본문 저장·색인 준비와 별개인 `pending | running | ready | needs_review | failed` 상태다. `ready`에는 주제가 없는 정상 완료도 포함한다. 모호한 연결은 확정하지 않고 `needs_review`와 미해결 힌트를 반환하며, 확인한 연결만 반영할 수 있다. 늦은 실패·완료가 최신 revision의 상태를 덮어쓰지 않도록 작업의 요청/반영 revision과 연결한다. 과거 저장본을 조회할 때 현재 작업 상태를 과거 결과인 것처럼 표시하지 않는다.

`concept_hints` 생략은 수정 시 기존 힌트를 유지하고, `[]`는 힌트를 비운다. 빈 힌트만으로 기존 연결을 모두 없앴다고 해석하지 않는다. 새 본문/힌트로 분류를 다시 할 때는 현재 연결도 후보로 평가한다. 순수 공개 범위·완료·유형 변경 때문에 새 의미 판단을 반복하지 않으며 미완료 작업이 버전 충돌한 경우에만 최신 대상으로 이어간다.

명시적 정정은 `capture_set_concepts(request_id, capture_id, ExpectedVersion, concept_ids, node_concepts?)`로 처리한다. `concept_ids`는 기록 주제의 전체 목록이며 `[]`는 비우기다. `node_concepts`는 생략하면 기존 Node 연결 유지, 제출하면 현재 Node별 `{node_id, concept_ids[]}` 전체 목록으로 교체하며 빠진 Node는 빈 연결로 처리한다. Node 소속·ID·조회 자격을 검증한다. 이 경로는 관리 화면의 선택·명시적 정정용이며 기본 저장의 선행 호출이 아니다. 결과는 새 `edit` revision으로 남기고 옛 자동 작업을 무효화하며 이 정정 자체로 재분류를 시작하지 않는다. 이후 사용자가 본문·힌트·Node를 바꾸면 그 새 저장 요청의 범위에서 다시 분류한다.

`concept_ids`는 읽기 결과·검색 필터·위 명시적 정정 계약에 유지한다. 생성·일반 수정·병합의 기본 입력에는 넣지 않는다. 내부 주제 판단 실패를 외부 LLM의 ID 탐색 의무로 되돌리지 않는다.

## 청크의 기준과 예산

규칙 버전은 `markdown-v1`이다. **Markdown 구조 → 문단/블록 → 문장 → 토큰** 순서로 분할한다. 분할은 결정적인 서버 로직으로 수행하며 별도 LLM 호출이나 본문 재작성을 사용하지 않는다.

| 항목 | 초기 규칙 |
| --- | --- |
| 최대 입력 | 실제 `encode_document` 경로의 제목·헤더 맥락·구분자·모델 마커·특수 토큰을 모두 포함해 512토큰 이하 |
| 짧은 기록 | 전체 입력이 예산 안이면 헤더 수와 관계없이 청크 하나 |
| 구조 경계 | 최상위 블록의 ATX `#`~`######`와 Setext 헤더. 헤더 레벨·본문 위치로 경로를 유지 |
| 작은 구간 | 원문만의 토큰 수가 각각 128 미만인 인접 형제 구간은 같은 부모 아래에서 합산 전체 입력이 512 이하면 순서대로 묶음. 최상위 형제도 같은 문서 루트 아래로 취급 |
| 큰 구간 | 블록을 원문 순서로 최대한 묶고, 예산을 넘는 단일 블록만 아래 규칙으로 분할 |
| 겹침 | 단일 문단·블록을 강제 분할할 때만 같은 구간 안에서 최대 64토큰. 독립 헤더·완결 블록 경계는 기본 0 |
| 보조 맥락 | 제목과 헤더 경로를 반복할 때 구분자 포함 최대 64토큰. 전체 입력 512 안에 포함 |

512는 모델 한계나 최적값으로 입증된 수치가 아니라 현재 개발 시작값이다. 1,024와 같은 자료에서 품질·CPU 지연·총 벡터 수·겹침을 비교할 수 있도록 프로필 값으로 관리한다. 모델의 공식 문서 한도는 8,192토큰이다. [KURE-v2 모델 카드](https://huggingface.co/nlpai-lab/KURE-v2)

## 헤더·블록 처리

1. 원문 위치를 보존하는 Markdown 파서로 구조를 읽는다. 단순히 줄 첫 글자 `#`로 분리하지 않는다. 코드 펜스·들여쓴 코드·인용·목록 안의 헤더는 문서 전체의 새 섹션으로 취급하지 않는다. 헤더와 코드의 문법 판정은 [CommonMark](https://spec.commonmark.org/0.31.2/#atx-headings), 표는 [GFM 표 확장](https://github.github.com/gfm/#tables-extension-)을 따른다.
2. 긴 기록에서는 다음 문서 헤더 직전까지를 기본 구간으로 둔다. 헤더 이전 서문도 구간이며, 헤더 레벨이 뛰어도 없는 부모 제목을 만들어 넣지 않는다. 헤더만 있고 본문이 없는 상위 구간은 이어지는 하위 구간과 붙여 고립된 제목 청크를 줄인다.
3. 각 구간에서 완결된 문단·목록·인용·코드·표를 순서대로 묶는다. 예산 안에 들어오는 블록은 쪼개지 않는다. 작은 형제 구간을 묶어도 각각의 헤더 경로·범위를 메타데이터로 남기고 다른 기록끼리는 절대 합치지 않는다.
4. 단일 문단이 예산을 넘으면 문장 끝을 우선한다. 그래도 긴 문장·URL·식별자는 토크나이저 offset을 원문 code point 위치로 변환해 안전한 문자 경계에서 분할한다. decode한 토큰 문자열로 정본을 다시 구성하지 않는다.
5. 긴 목록은 항목, 표는 행, 코드는 줄 경계를 우선한다. 항목·행·코드 한 줄도 너무 길면 마지막 수단으로 토큰/문자 경계 분할을 적용하고 `split_reason`에 표시한다. 표 헤더·코드 언어 등 반복 설명은 보조 맥락 예산을 공유한다. 반복 코드 펜스를 렌더링용으로 덧붙이면 보조 맥락으로만 취급하며 원문 span을 바꾸지 않는다.
6. 강제 분할 뒤에는 직전 구간 끝의 완결 문장/줄을 최대 64토큰까지 겹친다. 완결 단위가 너무 길면 안전한 문자 경계의 suffix를 쓴다. 전체 512 예산과 새 본문의 전진을 우선해 겹침을 줄이거나 0으로 만들 수 있다. 같은 범위만 반복하는 청크는 금지한다.
7. 실제 임베딩 입력을 다시 토큰화해 상한을 확인한다. 마커·특수 토큰을 이중으로 붙이지 않는다. 초과분은 다음 청크로 이동하며 모델의 자동 truncation에 맡기지 않는다.

제목·헤더 경로는 의미를 보조하며 자동 Concept나 Node를 생성하는 근거가 아니다. 보조 맥락이 64토큰을 넘으면 현재 헤더와 가까운 조상, 제목 순서로 예산을 배정하고 안전한 문자 경계에서 줄인다. 사용한 형태와 `context_truncated`를 남기며 전체 제목·헤더 경로는 메타데이터에서 유지한다. 본문 안의 원래 헤더는 일반 본문과 함께 빠짐없이 청크에 포함한다. 보조 맥락의 축약을 원문 누락으로 연결하지 않는다.

전체 기록 한 청크의 보조 맥락은 기록 제목만 사용한다. 작은 형제 구간을 묶은 청크는 공통 부모 경로와 제목을 사용하고 각 형제의 헤더는 원문에 남긴다. 그 밖의 청크는 현재 구간의 헤더 경로와 제목을 사용한다. 코드 언어·표 헤더 보조가 필요하면 같은 64토큰 예산에서 가까운 블록 맥락을 우선한다.

문장 경계 판정기·Markdown 파서·GFM 확장 설정·토크나이저 revision은 프로필에 고정한다. `markdown-v1`의 문장 경계는 문단 안의 종결 부호(`.`, `?`, `!`, `。`, `？`, `！`) 뒤 공백/구간 끝을 후보로 삼고 소수·URL·코드 span 내부는 후보에서 제외하는 규칙으로 시작한다. 문장 판정의 품질이 낮아도 원문 범위 누락·순서 변경은 허용하지 않는다.

## 원문 참조와 예시

각 청크는 한 revision의 연속적인 원문 범위 `[body_start, body_end)`를 가진다. 원본 청크 본문은 정확히 `body_markdown[start:end]`이며 공백·개행·Unicode를 재정규화하지 않는다. 파서가 내부적으로 개행을 정규화하더라도 원문 위치로 변환하는 매핑을 유지한다. 선행·후행·블록 사이 공백도 인접 청크에 포함해 본문 전체를 덮는다.

`section_refs[]`는 해당 청크와 만나는 섹션의 원문 범위·헤더 경로를 저장한다. `context_prefix`는 실제 임베딩에 사용한 보조 맥락, `context_truncated`는 축약 여부, `split_reason`은 `whole_record | section | packed_sections | block | sentence | token`이다. 제목/헤더를 여러 청크에 반복해도 실제 근거와 Node 매핑은 `body_start/end`로 계산하며 반복한 prefix에서 가짜 인용 위치를 만들지 않는다.

예를 들어 긴 학습 기록이 `# 트랜잭션 → ## 원자성 → ## 격리성`으로 구성되면 원자성과 격리성을 우선 별도 구간으로 다룬다. 격리성만 길면 그 구간을 문단·문장 순서로 나누고 각 청크에 `트랜잭션 > 격리성` 경로를 보조한다. 짧은 메모는 같은 헤더 구조가 있어도 한 청크에 보존한다. 검색 후에는 [맥락 계약](retrieval-and-context.md)에 따라 원본 Node·섹션·앞뒤 본문을 추가 조회할 수 있으며 청크 하나만으로 답변 맥락을 제한하지 않는다.

## 구현 시 검증할 조건

- 외부 ID 조회 없는 저장, 힌트 없음, 동일 이름의 다른 주제, 잘못된 힌트, Node만의 주제, 모델 미연결·실패에도 본문 보존.
- 자동 연결과 사용자 수정·삭제·주제 정정의 경합, 동일 job 재실행, 같은 주제 동시 생성, 이전 revision 불변, 자동 연결의 재귀 방지.
- 헤더 없는 본문, 중첩·Setext·동일 제목, 코드 안의 `#`, 인용/목록 안의 헤더, 긴 코드·표·URL, CRLF·이모지·결합문자.
- 같은 프로필/원문에서 결정적인 청크, 전체 원문 범위의 합집합 보장, 512토큰 상한, 겹침 상한·전진 보장, 작은 구간 묶기와 보조 맥락/인용 분리.
- 512와 1,024 비교 시 동일 문서·질문으로 정확도·맥락 누락·p95·총 청크/벡터 수·디스크를 함께 측정. 수치를 변경하기 전 동일 조건의 실행 평가가 필요하다.
