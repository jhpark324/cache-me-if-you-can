# 스키마의 서비스 적합성 검토

이 문서는 현재 구조에서 유지할 계약과 별도로 평가해야 할 품질·확장 과제를 설명한다. 실제 필드와 제약은 [데이터 스키마](data-schema.md), 실행 경계는 [현재 구조](current-system.md), 재현 절차는 [검증 안내](../guides/testing.md)를 따른다.

## 유지할 구조

Capture–Revision–Concept–선택적 Node–검색 청크는 저장 원문, 재사용 목적, 연결 의미, 검색 단위를 구분한다. 여섯 RecordKind는 복수 또는 미분류를 허용한다. 유형별로 별도 저장 테이블·CRUD·전용 에이전트를 둘 필요는 없다.

| 요소 | 역할 | 유지할 조건 |
| --- | --- | --- |
| 본문 필수, 유형·Node 선택 | 짧은 메모와 긴 정리본을 같은 경로로 저장 | 미분류 기록을 일반 검색에서 배제하지 않음 |
| 여섯 RecordKind | 지식·경험·맥락·아이디어·결정·자료의 재사용 목적 표현 | 유형만으로 사실성·채택·현재 적용을 추정하지 않음 |
| 동적인 Concept | 기록·Node의 주제와 별칭 연결 | 주제와 적용 대상·상황을 같은 것으로 간주하지 않음 |
| Markdown + 불변 Revision | 실제 저장본·정정·출처·변경 이력 보존 | 개별 기록의 최신 버전과 여러 기록 사이의 현재 유효한 주장을 구분 |
| SQLite 정본 + LanceDB 파생 검색 | 기록 보존과 검색 모델 변경 분리 | outbox·현재 revision·색인 세대 재검증, 두 DB의 원자적 커밋을 가정하지 않음 |
| `deleted_at` | 내부 이력·출처를 보존하면서 제품에서 제외 | 모든 조회·늦은 색인 작업에서 확인, 휴지통·복원 경로 없음 |

## 서비스 계약에서 지켜야 할 경계

### 저장과 상세 조회

목록은 짧은 후보 정보를 반환하고 상세 조회는 현재 본문·주제·출처·재검토 상태를 제공한다. 선택적 Node를 저장했다면 새 요청에서도 해당 본문 구간·유형·origin·verification을 확인할 수 있어야 한다. 모델이 누락된 구조를 추측해서 복원하게 만들지 않는다.

`concept_hints`의 서버 주제 연결은 본문 저장 뒤 수행한다. 실패하거나 후보가 모호해도 본문 저장을 취소하지 않는다. 자동 주제 연결은 Node의 의미 추출이나 본문의 사실성 검증을 뜻하지 않는다. [저장 후 처리](ingestion-and-chunking.md)

### 출처 정정과 파생 기록

원출처 A1로 만든 B가 있을 때 A2가 만들어졌다는 이유만으로 B의 출처를 조용히 최신본으로 바꾸지 않는다. 명시적인 `capture_review_sources`에서 새 B revision의 본문·출처를 함께 검토하고 이전 B revision의 A1 근거를 보존한다.

`sources: []`로 의존성을 지우는 우회는 허용하지 않는다. 출처를 변경했다는 사실만으로 본문 전체가 검증됐다고 표시하지 않는다. A 정정 → B 재검토 필요 → 명시적인 본문·출처 정정 → 새 B의 근거 사용 자격 확인을 함께 검증한다. [기록 명세](../specs/records.md)

### 현재 상황에 적용할 맥락

유형·주제·최신 revision만으로 적용 대상·시점·채택 여부를 확정할 수 없다. 본문의 주체·상황·시점과 근거 구간을 함께 읽어야 한다.

| 반례 | 필요한 판단 |
| --- | --- |
| 특정 여행의 예산을 다른 여행에 적용 | 어느 여행에 해당하는 조건인지 |
| 발표는 짧게, 학습 설명은 자세히 중 하나만 전역 선호로 적용 | 상황별 적용 범위 |
| 옛 선호와 변경한 선호가 각각 현재 revision | 명시적인 변경 관계·발언 시점. 저장 시각만으로 결정하지 않음 |
| AI 제안을 실제 실행 약속으로 사용 | 제안자·채택 여부·실행 여부 |
| 개념 설명을 저장한 사실을 완전한 이해로 판단 | 설명의 존재와 사용자의 이해 상태 |

`supersedes`는 명시적으로 바뀐 조건, `corrects`는 오류 정정의 의미를 보존해야 한다. 불명확한 맥락은 현재 적용 가능하다고 단정하지 않는다. 모든 기록에 단일 scope·중요도·신뢰도 점수를 강제해 이 문제를 해결하려 하지 않는다. [검색·맥락 계약](retrieval-and-context.md)

### Node·주제·관계

| 경계 | 유지할 조건 |
| --- | --- |
| 청크 → Node | 같은 revision의 본문 구간으로 연결한다. 청크 점수를 모든 겹친 Node의 독립적인 관련성 점수로 복사하지 않음 |
| Node 편집 | 본문이 바뀌면 span을 재검증한다. 과거 Node 보존과 현재 Node 유효성을 구분 |
| 주제 | 부모 기록의 주제를 모든 Node의 주제로 추정하지 않음. 목록·검색·그래프 필터는 현재 Node 주제도 일관되게 반영 |
| 관계 승계 | 본문 불변 메타데이터 변경과 실제 본문 변경의 승계·재검토 규칙을 구분 |
| 그래프 확장 | 실제 저장된 관계만 사용하고 반환 예산·잘림·현재성 검사를 유지 |

## 별도로 평가할 항목

자동 계약 검증과 실제 검색·분류 품질 평가는 구분한다. 미분류 메모, 학습·감정 혼합 기록, AI 제안과 사용자 선택, 범위가 다른 선호, 명시적인 변경, 출처 정정, 본문 수정 뒤 Node 처리, 삭제 후 재노출 방지를 대표 사례로 삼는다.

시점 추론·정보 갱신·근거 부족 시 응답 보류는 서로 다른 실패 유형이다. [LongMemEval](https://arxiv.org/abs/2410.10813)의 평가 구분을 참고할 수 있지만 논문의 성능을 제품 성능으로 옮겨 주장하지 않는다. 실제 사용자 자료의 품질과 큰 저장소의 비용은 아직 별도로 측정해야 한다.

구체적인 책임 분리와 규모 확장 순서는 [유지보수 점검](maintenance-review.md), 도입하지 않은 제품 기능은 [발전 제안](../project/evolution-proposals.md)에서 관리한다.
