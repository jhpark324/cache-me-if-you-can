# 스키마의 서비스 적합성 검토

- 검토일: 2026-11-02
- 상태: 구현 전 설계 검토의 이력. 이후 제품 구현·검증은 [004](../specs/004-local-runtime/validation.md), 현재 구조는 [구현 구조](current-system.md) 참조
- 대상: [기록 유형](../project/record-types.md), [저장 스키마](data-schema.md), [MCP·웹 계약](service-contracts.md), [제품 방향](../project/product-brief.md)

## 판단

아홉 RecordKind와 Capture–Revision–Concept–선택적 Node–검색 청크의 기본 구조는 서비스에 적합하다. 최초 검토에서는 에이전트가 저장된 내용을 반복해서 읽고 정정하며 **이번 질문에 적용할 맥락**을 고르기 위한 계약의 빈틈을 확인했다. 이후 문서 계약을 보완했으며 실제 동작과 검색 품질은 아직 검증하지 않았다.

아래 보완 항목은 최초 검토 당시의 발견과 권고를 보존한다. 현재 계약의 반영 여부는 다음 표와 연결된 명세를 따른다. 계약 반영을 제품 구현 완료로 해석하지 않는다.

## 후속 기획 반영

| 검토 항목 | 현재 반영한 계약 | 남은 검증 |
| --- | --- | --- |
| 상세 조회 | Capture 상세의 주제·출처·재검토 상태와 Node 상세, 목록·상세 응답 분리 | 저장 후 같은 구조를 다시 읽는 왕복 검증 |
| 출처 정정 후 재검토 | 명시적인 `capture_review_sources`로 새 revision의 본문·출처 갱신, 이전 revision의 근거 보존 | 실제 출처 갱신·권한·동시성·QA 재진입 검증 |
| 적용할 맥락 선택 | 출처·범위·시점을 함께 반환하는 맥락 후보, 범위가 명시된 `supersedes`, 관계 철회 | AI 제안·선택 구분과 상황별 적용 판단 평가 |
| Node·주제·관계 | Node 상태와 개별 주제, 주제 CRUD 계약, 청크 구간 매핑, 안전한 메타데이터 변경의 승계 조건 | span 정확도·검색 누락·오래된 관계 노출 검증 |
| 서버 주제 연결·청크 | [concept_hints와 서버 후속 연결, Markdown 구조 기반 분할](ingestion-and-chunking.md). 초기 검토의 외부 concept_ids 입력을 기본 저장 계약에서 대체 | 실패 시 본문 보존·주제 정정 경합·전체 원문 청크 포함·512토큰 상한 검증 |
| 삭제 | 재확인 후 `deleted_at`만 설정하고 모든 제품 조회에서 제외. 휴지통·복원 없음 | 삭제 후 검색·직접 조회·인용 패널·늦은 작업의 재노출 방지 |

공통 기준은 [데이터 스키마](data-schema.md), [서비스 계약](service-contracts.md), [검색·맥락 계약](retrieval-and-context.md)에 반영했다. 기록 관리의 수용 기준과 구현 작업은 [002 기능 명세](../specs/002-record-management/index.md), 후속 검색·웹 작업 순서는 [MVP 작업 계획](../plans/mvp-delivery.md)에서 관리한다.

## 유지할 구조

| 요소 | 적합한 이유 | 조건 |
| --- | --- | --- |
| 아홉 RecordKind | 학습·감정·경험·계획·조건·아이디어·결정·재사용 자료를 표현 가능 | 선택적 다중 라벨로 사용. 실제 분류·검색 효용은 아직 측정하지 않음 |
| 본문 필수, 유형·Node 선택 | 짧은 메모와 긴 정리본을 같은 입력 경로에서 저장 가능 | 미분류 기록을 일반 검색에서 배제하지 않음 |
| 동적인 Concept | 공부·일상·업무 등 분야를 enum에 계속 추가할 필요 없음 | 주제와 적용 대상·범위를 같은 것으로 간주하지 않음 |
| 전체 Markdown + Revision | 사용자 확인·정정·출처 참조·변경 이력을 지원 | 개별 기록의 최신 revision과 여러 기록 중 현재 유효한 주장을 구분 |
| `deleted_at` 기반 soft delete | 본문·관계·이력을 내부 보존하면서 제품에서는 삭제 처리 | 모든 조회 경로와 늦은 색인 작업에서 삭제 상태 확인. 휴지통·복원은 제공하지 않음 |
| SQLite 정본 + LanceDB 파생 검색 | 전체 기록을 보존하면서 청크로 관련 부분을 찾는 요구에 부합 | 색인 작업·현재 revision·세대 검증을 구현해야 하며 두 DB의 원자적 커밋을 가정하지 않음 |

`knowledge–procedure–artifact`, `idea–plan`, `episode–reflection`은 실제 기록에서 겹칠 수 있다. 이를 이유로 당장 유형을 합치지는 않는다. 주요 목적과 분명한 부목적만 부여하고, 실제 저장 사례에서 과도한 다중 분류와 검색 도움 여부를 평가한 뒤 통합을 판단한다. 기록 유형별로 별도 저장 테이블·CRUD 흐름을 만드는 것은 권하지 않는다.

## 최초 검토 — 저장·조회·정정 MVP의 보완 권고

### 1. 저장한 메타데이터를 다시 읽는 상세 조회

[CreateCaptureInput](service-contracts.md#생성수정-요청)은 Node·주제·출처를 받지만 [CaptureView](service-contracts.md#공통-타입)의 명시 필드에는 이 정보가 빠져 있다. 정리본에 맥락이 남을 수는 있으나, 이후 에이전트와 웹이 저장된 구조를 그대로 회수하고 정정할 계약이 부족하다.

권고: 상세 조회에서 저장된 주제·출처·재검토 상태를 반환하고, Node를 사용할 때 해당 Node의 구간·종류·origin·확인 상태를 읽을 수 있게 한다. 목록·검색 결과에 모든 데이터를 실을 필요는 없다. 짧은 후보 조회 후 상세 내용을 읽는 기존 흐름을 유지한다.

수용 사례: 에이전트가 Node·주제·출처를 포함해 저장한 뒤 새 요청으로 조회했을 때, 새로 추측하지 않고 같은 메타데이터를 확인할 수 있어야 한다.

### 2. 원출처 정정 후 파생 지식을 다시 검토하는 경로

현재는 원출처의 revision이 바뀌면 파생 기록을 QA 근거에서 제외한다. 일반 PATCH는 기존 출처를 보존하고 새 출처를 추가하는 규칙이므로, **A1로 만든 B를 A2에 맞춰 정정해도 A1 의존성이 남아 계속 제외될 수 있다.** 별도 재검토 계약이 필요하다고 문서에 적혀 있지만 아직 동작을 정하지 않았다. 제목·유형 변경도 revision을 만들므로 운영 중 자주 발생할 수 있다.

권고: 명시적인 재검토에서 새 B revision의 본문과 출처를 함께 갱신할 수 있게 한다. 이전 B revision에는 A1과 과거 판단을 보존한다. `sources: []`만으로 의존성을 지우는 우회는 유지하지 않으며, 출처를 바꿨다는 이유만으로 본문까지 자동 검증됐다고 처리하지 않는다.

수용 사례: A 정정 → B 재검토 필요 → 명시적 정정·새 출처 확인 → 새 B를 QA에서 활용하는 전체 흐름이 가능해야 한다. 이력과 실제 사용한 근거는 남아야 한다.

### 3. 에이전트가 이번 상황에 사용할 맥락의 선택

아홉 유형만으로 적용 대상·시점·채택 여부를 알 수 없다. [유형 설계의 원칙](../project/record-types.md#에이전트-컨텍스트에-사용하는-규칙)은 필요하지만 이를 조회 응답·후속 읽기·충돌 처리까지 연결해야 한다.

| 반례 | 필요한 판단 |
| --- | --- |
| “이번 제주 여행 예산은 50만 원”을 다른 여행에 적용 | 어느 여행의 조건인지 |
| “발표 자료는 짧게”와 “학습 설명은 자세히” 중 하나만 전역 선호로 적용 | 상황별 적용 범위 |
| 별도 기록에 저장한 옛 선호와 명시적으로 변경한 선호가 모두 현재 revision | 변경 관계·발언 시점. 저장 시각만으로 결정하지 않음 |
| AI가 제안한 계획을 사용자의 실행 약속으로 사용 | 제안자·채택 여부·실행 여부 |
| 개념 설명과 남은 질문을 저장했는데 이미 완전히 이해했다고 판단 | 설명의 존재와 사용자의 이해 상태 |

권고: 조회한 구간의 주체·상황·시점·제안/채택 구분을 알 수 있는 문맥과 출처를 함께 읽고 전달한다. 명시적인 조건 변경은 같은 범위의 이전 기록과 연결하는 계약을 정한다. 과거에 맞았던 선호가 바뀐 경우와 사실 오류를 정정하는 경우의 의미도 구별한다. 불명확하면 현재 적용 가능하다고 단정하지 않는다.

처음부터 모든 기록에 scope·유효 기간·중요도·신뢰도 점수를 필수로 추가할 필요는 없다. 본문에 알려진 범위를 보존하고 명시적인 변경·충돌을 처리하는 첫 계약부터 만든다. 자동으로 프로젝트별 맥락을 선별하는 기능을 제공할 때에는 구조화된 범위가 필요할 수 있다. 혼합 기록에는 서로 다른 사람·프로젝트의 정보가 있을 수 있으므로 기록 전체에 단일 scope를 붙이면 해결된다고 가정하지 않는다.

시간 추론·지식 갱신·근거 부족 시 응답 보류는 장기 기억 연구에서도 구분해서 평가한다. 이를 별도 수용 사례로 삼는 것이 위 권고의 근거이며, 논문의 성능을 우리 제품의 성능으로 옮겨 주장하지 않는다. [LongMemEval, ICLR 2025](https://arxiv.org/abs/2410.10813)

## 최초 검토 — Node·주제·그래프의 보완 권고

이 항목들은 본문 저장·검색을 먼저 구현하는 것을 막지는 않지만, Node 검색이나 주제 그래프가 제공된다고 표시하기 전에는 필요하다.

| 항목 | 검토 당시 빈틈 | 최소 보완 방향 |
| --- | --- | --- |
| 청크 → Node 검색 | 청크에는 revision·본문 위치가 있고 Node 참조는 선택적이다. 여러 Node와 겹칠 때의 결과 단위·점수 규칙이 없음 | 같은 revision의 구간 매핑, Node 직접 조회, Node가 없거나 여러 개일 때의 반환 규칙. 청크 점수를 각 Node의 관련성으로 그대로 복사하지 않음 |
| Node 편집 | 본문 변경 시 Node를 생략하면 새 revision의 Node가 비워짐 | 잘못된 span을 재사용하지 않는 원칙 유지. 정정 화면·도구에서 Node 재제출/재검증 또는 현재 구조가 제거된 사실을 명확히 처리. 과거 Node의 보존만으로 현재 Node 검색이 유지되는 것은 아님 |
| 주제 생성·탐색 | 생성 입력은 기존 concept_ids를 받지만 주제 생성·탐색 도구는 후속 계약 | 빈 저장소에서 주제를 만들고 찾아 연결하는 경로. 본문만 저장하는 흐름의 선행 조건으로 만들지 않음 |
| 관계 입력·승계 | 관계 도구가 미정이고 현재 revision만 표시하므로 유형만 변경해도 옛 revision의 관계가 기본 그래프에서 빠질 수 있음 | 본문 불변 변경과 실제 내용 변경의 관계 승계·재검토 규칙을 구분 |
| Node별 주제 | 현재 Concept 연결은 revision 단위 | Node별 태그를 제공한다면 별도 연결을 정의. 부모 기록의 모든 주제를 모든 Node의 주제로 추정하지 않음 |

## 구현 범위를 늘리지 않아도 되는 부분

- 아홉 유형 각각의 전용 테이블·화면·에이전트를 만들지 않는다.
- 모든 문장을 Node로 추출하거나 저장 전 필수 LLM 재분류를 두지 않는다. 후속 사용자 결정의 서버 주제 연결은 저장 후 별도 작업이며 본문·Node 의미 재추출과 구분한다.
- 자동 프로필 병합, 사용자 성향 추론, 고정된 중요도·신뢰도 점수는 첫 계약에 추가하지 않는다.
- 일정 관리, 자동 삭제·영구 삭제, 실제 공유 권한 체계를 이번 검토로 도입하지 않는다.
- 색인 재시도·현재 상태 확인은 유지하되, 분산 작업 시스템이나 자동 다중 모델 전환으로 범위를 확장하지 않는다.

## 후속 검증 범위

본문만 저장한 미분류 메모, 학습·감정 혼합 기록, AI 제안과 사용자 선택, 적용 범위가 다른 선호, 명시적인 선호 변경, 원출처 정정과 파생 지식 재검토, 본문 수정 뒤 Node 처리, 삭제 후 모든 조회·검색·출처 패널에서의 재노출 방지를 대표 수용 사례로 삼는다.

이번에 수행한 것은 문서 간 계약 대조와 사례별 설계 검토, 후속 계약·기능 명세 작성이다. 실제 분류 정확도, 검색 품질, CPU 지연, 마이그레이션·동시성·Codex 연동을 시험한 결과가 아니다. 작성한 기능 명세를 실제 구현으로 검증한 뒤 구현 적합성을 판단한다.
